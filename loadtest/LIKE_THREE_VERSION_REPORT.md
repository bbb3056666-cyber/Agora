# 单视频点赞三版本对比（2026-10-26）

## 口径与环境

目标是区分 **HTTP 已受理** 和 **数据库已落实**，不是只比较接口返回速度。Windows 主机运行 k6 2.3.0，Ubuntu VM 运行 Nginx、3 个 API、1 个 Worker、MySQL 8、RabbitMQ 和 Redis。主机与 VM 仍共用一台物理电脑，测试不是独立物理压测机，也不是生产容量承诺。

三个版本：

1. **同步基线**：为本次对照从优化版源码构建，见分支 `bench/like-sync-baseline`、提交 `1745520`。HTTP 事务内更新点赞关系、视频计数并写入后续 Outbox，提交后返回 `200 APPLIED`。这不是 Git 中某个已存在的历史“最初版”提交；仓库最早的点赞代码已经采用异步链路。
2. **原异步版**：本次测试开始时 VM 正在运行的版本，基于 `1a02fd5` 及 VM 上原有未提交改动。API 写最新点赞意图和 Outbox 后返回 `202 PENDING`；Worker 逐条落实，同一视频的计数行每次更新一次。
3. **批量分区版**：`main` 提交 `7b1c66e`。按内容 ID 分区、单活消费者串行处理同一分区；短时间收集同内容消息，按真实状态变化合并为一次视频计数更新。仍是异步 `202 PENDING`。

各档都用同一批 20,000 个测试账号，每档换一条无点赞关系、`likes_count=0` 的视频；纯 POST 点赞，单条视频、无取消。k6 使用 `constant-arrival-rate`，预建及最大 VU 均为目标 QPS 的两倍，请求超时 5 秒。每个账号在同一档只点赞一次；没有把重复点赞算作有效处理量。采样脚本每约 1.1 秒查询目标视频的 `desired_liked`、`is_liked` 和 `likes_count`；差值表示已接受但尚未落实的点赞意图。每档停压后等待追平，再开始下一档。

复现命令示例（本机 `loadtest` 目录）：

```powershell
$env:QPS='500'; $env:DURATION='30s'; $env:VUS='1000'
$env:CONTENT_ID='885024'; $env:CONTENT_COUNT='1'; $env:UNLIKE_PERCENT='0'
$env:EXPECTED_STATUS='202' # 同步基线设为 200
& F:\GoProjects\.tools\k6-v2.3.0\k6-v2.3.0-windows-amd64\k6.exe run --summary-export results\compare-opt-500-summary.json .\like.js
```

VM 采样命令：`cd /opt/agora && python3 /tmp/compare-like-state.py sample <CONTENT_ID> 45 1`。`loadtest/compare-like-state.py` 是脚本源文件，压测令牌仅放在 Git 忽略的 `loadtest/generated/`；`results/` 保留原始 k6 log/JSON、时序 TSV 和两个源码归档，不提交含测试数据的大文件。

## 实测结果

| 版本 | 目标 QPS / 时长 | 成功响应 | 未发出 / HTTP 失败 | HTTP P99 | 运行中最大未落实 | 停压后数据库 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原异步版 | 500 / 30s | 15,001 | 0 / 0 | 11.54 ms | 7,825，持续增长 | 15,001 条追平 |
| 批量分区版 | 500 / 30s | 15,000 | 0 / 0 | 10.42 ms | 约 464，短时波动 | 15,000 条追平 |
| 批量分区版复测 | 500 / 30s | 15,001 | 0 / 0 | 9.48 ms | 333，集中在启动阶段 | 15,001 条追平 |
| 同步基线 | 500 / 30s | 15,001 | 0 / 0 | 1.49 s | 0，响应前已提交 | 15,001 条一致 |
| 批量分区版 | 600 / 30s | 18,000 | 0 / 0 | 11.68 ms | 603，未持续扩大 | 18,000 条追平 |
| 批量分区版 | 700 / 25s | 17,501 | 0 / 0 | 13.83 ms | 1,527，后半段增大 | 17,501 条追平 |
| 批量分区版 | 1,000 / 18s | 18,001 | 0 / 0 | 17.99 ms | 6,081，明显持续增长 | 18,001 条追平 |
| 同步基线 | 800 / 20s | 11,982 | 2,279 / 1,740 | 5 s 超时截断 | 不适用 | 11,983 条已提交 |

同步版 500 档虽然计划中的 15,001 次都发出并成功，因请求在结束后继续等待，k6 统计区间内的平均完成速率约 482.7/s，P99 远高于异步两版。800 档预建 VU 为 1,600，因请求大量接近 5 秒超时而用满，出现 2,279 次 `dropped_iterations`；它们是**压测端未发出**，不可算成服务端失败。1,740 次已发请求失败/超时。数据库最终比成功响应多一条，说明至少存在请求已提交但客户端未及时收到成功响应的情况；不能把客户端超时等同于事务必定回滚。

异步两版的 HTTP P99 均较低，但 `202` 只说明意图持久化。旧版 500 档后台未落实数持续增至 7,825，实际落实速度明显小于受理速度；批量分区版同档及复测的大部分采样只差几十条，后续全部落实。首次优化版 500 档的采样输出仅保留在执行记录中，复测的完整时序已保存为 `results/compare-opt-500-repeat.tsv`。优化版 600 档在 30 秒内未见持续扩大的积压；700 档后半段已有约 1,500 条积压，1,000 档增至约 6,000。故本次只能说**单视频纯点赞短测已验证 600 QPS / 30 秒**，700 及以上开始表现出不同程度后台排队；不能把 1,000 QPS 的零 HTTP 失败误称为完整处理能力，更不能推断长期上限。

## 一致性与部署检查

- 最终查询八条测试视频，`like_states` 中 `desired_liked`、`is_liked` 与 `contents.likes_count` 均相等；对应数量依次为 15,001、15,000、15,001、18,001、15,001、11,983、17,501、18,000。Outbox 待处理数均为 0，点赞主队列、分区队列、重试队列和死信队列最终均为 0。
- 切换同步基线后，测试结束已把三个 API 恢复为优化版镜像；Worker 一直是优化版。最终 3 API、Worker、Gateway、MySQL、RabbitMQ、Redis 全部健康，`/healthz` 返回 `{"status":"ok"}`。
- 第一次从 Windows `git archive` 部署优化版时，归档中的 `docker-entrypoint.sh` 带 CRLF，容器启动报 `exec ... no such file or directory`。仅在独立部署副本中转成 LF 后重建，恢复正常；仓库补了 `.gitattributes` 固定该脚本为 LF。所有部署从独立目录构建，原 `/opt/agora` 的源码及未提交改动没有被覆盖。

## 结论与限制

这次优化的收益主要是**减少热点内容行的更新次数，提升后台落实能力**，而不是显著降低 HTTP 受理延迟。同步基线在 500 QPS 时已出现秒级尾延迟，800 QPS 时因行锁排队导致请求超时与 VU 用尽；旧异步版把同一压力转移为 Worker 队列积压；批量分区版在相同 500 QPS 下明显缩小积压，并在 600 QPS 短档基本追平。

这里的同步基线是为控制变量专门构建，并不代表历史上真实运行过的原始版本；三版还存在代码结构和消息处理语义差异。负载只有单视频纯点赞，不涵盖取消、重复请求、多个热点视频、通知消费长时间负载或故障恢复。各档只跑 18～30 秒，后续若要给出可靠的长期工作点，应扩大测试账号池，并进行更长时间复测，同时记录从 `202` 到 `is_liked` 落实的逐请求延迟。不要拿本表直接写成生产环境的最高 QPS。

## 批量关系 SQL 优化与复测（2026-10-26）

在批量分区版上继续优化 Worker 的落实事务，代码提交 `d79beab`。之前一批 N 个不同用户虽然只更新一次视频计数，但仍逐个执行 N 次 `SELECT ... FOR UPDATE` 和 N 次 `UPDATE like_states`。现在先按账号去重、排序，一次锁定整批关系；在内存计算每个真实状态变化，再一次批量更新变化的关系。`like_applied` 事件仍批量写入 Outbox，视频计数仍在事务末尾更新一次，事务提交后才 Ack。对一批最多 32 条消息，关系处理从约 `2N` 条 SQL 降为 1 条查询 + 1 条更新；不改变 API `202` 语义或消息协议。

验证：`go test ./...`、`go test -race ./...`、`go vet ./...` 均通过。真实 MySQL 集成测试在固定前缀的独立测试库里验证了 32 人混合点赞/取消、重复投递幂等、缺失关系整批回滚和缺失内容回滚；测试后删除该测试库。运行中的三台 API、Nginx 与中间件未换，只从独立目录 `/home/deploy/agora-compare-bulk` 重建并替换 Worker。旧 Worker 镜像保存为 `agora-worker:compare-prebulk` 供回退。

同样使用一条全新零点赞视频、20,000 个已有账号、`constant-arrival-rate`、纯首次点赞，结果如下。表中的“峰值未落实”来自约每 1.1 秒一次的数据库采样，不能当作每一瞬间的精确峰值；最终再次核对了目标视频的期望状态、实际状态和视频计数。

| 目标 QPS / 时长 | 旧批量分区版：HTTP P99 / 采样峰值未落实 | 新批量关系 SQL 版：HTTP P99 / 采样峰值未落实 | 新版最终结果 |
| --- | ---: | ---: | --- |
| 600 / 30s | 11.68 ms / 603 | 9.80 ms / 24 | 18,001 次成功，关系与计数追平 |
| 700 / 25s | 13.83 ms / 1,527 | 29.37 ms / 835（完整窗口复测） | 17,501 次成功，关系与计数追平 |
| 1,000 / 18s | 17.99 ms / 6,081 | 77.64 ms / 2,206（完整窗口复测） | 18,001 次成功，关系与计数追平 |
| 1,500 / 12s | 未测 | 47.21 ms / 617 | 18,001 次成功，关系与计数追平 |

所有新档位均无 HTTP 业务失败或 `dropped_iterations`。100 QPS / 10 秒的冒烟档位另外完成 1,001 次，数据库计数一致。首次 700 和 1,000 QPS 的采样窗口在全部请求结束前停止，曾分别得到 32 和 600 的较低观测值；这些原始文件仍保留，但**不用于上表峰值结论**，上表采用延长采样窗口后的复测。700 和 1,000 QPS 复测的 HTTP P99 也高于首次测试，反映出共享物理主机和短时负载的波动。1,500 QPS 仅运行 12 秒且结果好于某些低档，不能据此认定系统存在单调提升的容量曲线，更不能宣称长期稳定处理 1,500 QPS。

目前可以确认：减少批内逐条关系 SQL 后，在相同短测负载下后台积压显著缩小，尤其 600 QPS 档几乎同步追平；但 700 和 1,000 QPS 仍会出现短时积压，改善并未消除所有瓶颈。下一步若需确定长期稳定点，应扩大账号池以避免重复点赞成为空操作，使用更独立的压测机跑分钟级负载，并记录实际批大小、Worker 事务阶段耗时及从 `202` 到 `is_liked` 生效的延迟。原始 k6 log/JSON、数据库 TSV 与源码归档在本机 `loadtest/results/compare-bulk-*`；短期 JWT 仍只在 Git 忽略目录。
