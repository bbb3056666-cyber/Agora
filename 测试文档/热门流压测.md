# 热门流压测

## 当前测试目标

对象：`POST /feed/listByPopularity`。

本轮先准备“登录用户读取第一页热门流”的正常热路径数据。登录请求会进入 `BatchGetLiked`，因此能够覆盖热门流的 Redis 热榜读取、视频实体缓存读取与批量点赞状态查询；不测 Redis 不可用后的 MySQL 回退、分页边界、非法参数、MQ 消费吞吐或热榜实时更新。

## 真实调用链

```text
POST /feed/listByPopularity
→ backend/internal/module/feed/handler.go：FeedHandler.ListByPopularity
→ backend/internal/module/feed/service.go：FeedService.ListByPopularity
  → 读取当前分钟及之前 59 个 Redis 分钟桶
  → 不存在快照时 ZUNIONSTORE 生成 5 分钟快照
  → 从快照 ZSET 取第一页 video ID
  → GetVideoByIDs（本地缓存 → Redis → MySQL）
  → buildFeedVideos
  → LikeRepository.BatchGetLiked（登录用户的批量点赞状态查询）
→ JSON 响应
```

## 固定请求条件

```json
{
  "limit": 20,
  "as_of": 0,
  "offset": 0
}
```

- 方法与路径：`POST /feed/listByPopularity`
- 请求头：`Authorization: Bearer <固定夹具中的登录用户 Token>`
- 首页由服务端确定 `as_of`；正式压测脚本应先预热一次，以生成当前分钟的合并快照。

## 数据集

| 数据 | 数量 | 用途 |
| --- | ---: | --- |
| 热榜作者 | 100 | 提供多作者的视频来源 |
| 热榜视频 | 2,000 | MySQL 视频实体与缓存读取样本 |
| Redis 热榜候选视频 | 1,200 | 60 分钟窗口合并后的候选集合 |
| Redis 分钟桶 | 60 | `v1:hot:video:1m:{yyyyMMddHHmm}` |
| 每桶热度成员 | 400 | 合计约 24,000 条分钟热度样本，模拟互动在窗口内分布 |
| 登录测试用户 | 100 | 轮换 Token，避免单用户限流影响结论 |
| 每位用户的点赞关系 | 20 | 对当前热榜首页候选点赞，保证 `BatchGetLiked` 返回真实结果而非空查询 |

数据生成器：`backend/cmd/seedpopularity/main.go`。

执行命令（在 `backend` 目录）：

```powershell

```

生成结果：

- MySQL：带 `popularity_loadtest` 前缀的账户、视频和点赞关系；
- Redis：当前分钟向前 60 个分钟桶；
- 夹具：`loadtest/generated/popularity_hot_fixture.json`，包含 100 个登录用户 Token；
- 当前分钟的合并快照会被删除，供下一次热门流请求重新生成。

## 压测脚本

`loadtest/popularity_hot.js` 使用 k6 的 `constant-arrival-rate` 模式：轮换 100 个登录用户，以固定到达率持续请求第一页；每次响应必须是 HTTP 200、20 条唯一视频，且每条均带有合法的 `is_liked` 状态。登录请求会实际执行 `BatchGetLiked`，但不要求热榜排序变化后每一条仍是该用户已点赞的视频。

正式压测前先请求一次接口得到 `as_of`，并将该值通过 `AS_OF` 环境变量传入 k6。这样所有请求读取同一份已预热的 5 分钟快照；`as_of=0` 只用于预热，不能用于本轮正常热路径的正式结果。

## 快照固定与有效结果

第一次低负载预检时脚本传入 `as_of=0`。该值会在跨分钟时重新选择当前快照，可能把 `ZUNIONSTORE` 的合并写入成本混入读取测试，因此不作为本轮“已预热热榜快照”正常路径的正式结论。

最终复测先以 `as_of=0` 请求一次接口完成预热，取得 `as_of=1788141720`；之后 k6 的所有请求固定传该值，只读取同一份已有快照。

| 目标 QPS | 实际 QPS | P95 | P99 | 错误率 | 最大 VU | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 2,000 | 1,999.89 | 未单独记录 | 6.93 ms | 0% | 8 | 通过 |
| 3,000 | 2,999.87 | 5.44 ms | 13.13 ms | 0% | 109 | 通过 |
| 4,000 | 3,757.76 | 33.44 ms | 295.94 ms | 6.3456% | 2,499 | 不通过；未维持目标到达率 |

### 结果与证据

- 本测试条件下，`POST /feed/listByPopularity` 的稳定正常热路径能力为 **3,000 QPS**；性能拐点位于 **3,000～4,000 QPS**。
- 4,000 QPS 时，k6 已将并发 VU 拉到 2,499，仍只完成约 3,758 QPS，同时 P99 与错误率均突破通过标准，属于明确饱和状态。
- API 的 `/debug/db/stats` 是累计值。固定快照 4,000 QPS 后，累计 `WaitCount=6,338`、`WaitDuration=47,286 ms`；随后的 3,000 QPS 档没有继续增加。这支持高压下存在连接池等待，但因为 4,000 QPS 档开始前没有单独记录零点，不能把全部累计等待严格归因于该档。
- 另一次 5,000 QPS 的辅助诊断采样（未固定 `as_of`，不用于上述正式吞吐结论）中，容器 CPU 约为：API 600%～645%、MySQL 256%～274%、Redis 53%～55%。说明进入高压后 API 与 MySQL 都是重要消耗点，Redis 并非首先饱和。
- 该辅助采样的 API CPU profile 没有有效样本，原因是 profile 与远端任务实际结束时间未完全重叠；因此不以该 profile 推断具体函数热点。

## 本轮结论边界

结论只适用于：单 API 实例、单 MySQL/Redis 实例、预热后的 Redis 热榜快照、登录用户首页请求、20 条视频、固定的 2,000 视频与 1,200 热榜候选数据集。它不代表热榜快照首次构建、Redis/MySQL 故障回退、翻页、热度写入 Worker 或生产集群的能力。

## 结果分析

### 1. 稳定能力与性能拐点

在“登录用户读取第一页、热榜快照已预热”的固定条件下，3,000 QPS 稳定通过，4,000 QPS 明显失稳，因此本轮稳定能力为 3,000 QPS，性能拐点位于 3,000～4,000 QPS。

4,000 QPS 并非只是平均响应略慢：P99 从 3,000 QPS 的 13.13 ms 跳至 295.94 ms，且错误率升至 6.3456%。这表示尾部请求已经开始排队，不能再按稳定服务能力计算。

### 2. 4,000 QPS 时的现象

- k6 目标为每秒持续发起 4,000 次请求，但实际仅完成约 3,758 QPS，说明系统不能维持该输入速率；
- k6 的最大活跃 VU 达到 2,499，说明请求处理变慢后，需要持续增加在途请求才能追赶目标到达率；
- P95 为 33.44 ms、P99 为 295.94 ms：多数请求仍可快速完成，但少量请求已出现明显等待；
- 错误主要表现为压测机收到 TCP `connection refused`；压测后 API 容器仍健康，未观察到容器重启或 OOM，因此不能把它归因为进程崩溃，更可能是高压下连接接纳能力不足。

### 3. 依赖组件与瓶颈证据

辅助高压采样中，API CPU 约为 600%～645%，MySQL CPU 约为 256%～274%，Redis CPU 约为 53%～55%。因此高压时 API 与 MySQL 都是主要消耗点，Redis 有负载但并非最先饱和。

API 的 Go 数据库连接池累计统计为 `WaitCount=6,338`、`WaitDuration=47,286 ms`，表明压测过程确实发生过等待数据库连接。但该指标是累计值，4,000 QPS 档开始前没有单独记录零点，不能把全部等待严格归因于该档，也不能据此断言连接池是唯一瓶颈。

当前更准确的判断是：高压下 API 处理、MySQL 点赞关系查询与连接池等待、服务连接接纳共同造成排队和尾延迟恶化。

### 4. 热榜为何仍会使用 MySQL

热榜视频 ID 来自 Redis 快照，但本轮使用登录用户请求，每次都会执行：

```text
Redis 热榜快照
→ 视频实体缓存读取
→ BatchGetLiked 批量查询 MySQL 点赞关系
```

因此该接口不是纯 Redis 读取。热榜排序主要由 Redis 承担，但 `is_liked` 状态仍持续使用 MySQL 连接与查询能力。

### 5. 最终结论

本轮最终结果固定了预热后的 `as_of`，所有正式请求读取同一份已有热榜快照，未把跨分钟的 `ZUNIONSTORE` 快照构建成本混入正常读取路径。

在此范围内，`POST /feed/listByPopularity` 的稳定能力为 3,000 QPS；4,000 QPS 时进入明显饱和状态。后续若优化，应先通过每档开始与结束的连接池增量、有效 CPU profile 和 MySQL SQL/慢查询证据进一步缩小瓶颈范围，而不是直接假定某一个组件是唯一原因。
