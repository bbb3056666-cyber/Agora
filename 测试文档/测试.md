### 推荐的第一个测试对象

接口：`POST /feed/listLatest`

选择理由：这是核心 Feed 读链路，实际会经过 Redis 全局时间线、L1 本地缓存、Redis、MySQL 三级视频缓存及冷数据兜底，能覆盖最多核心组件。

主要性能风险：缓存未命中时的并发回源；Redis 时间线读取与批量实体获取；MySQL 冷数据查询；视频列表组装和 JSON 序列化。

后续需要重点观察的组件：Redis 全局时间线与详情缓存、进程内 L1 缓存、MySQL 视频查询与连接池、API 进程 CPU/内存、请求延迟和错误率。

## 压测时的观测清单

压测不能只看“跑出了多少 QPS”。每一轮应将压测机、API、MySQL、Redis 与异步链路的数据分开记录，才能判断是哪一环先到上限。

### 1. k6：接口结果与压测机

| 看什么 | 含义 | 需要警惕的现象 |
| --- | --- | --- |
| 实际 QPS | 实际完成的请求速率 | 明显低于目标 QPS，说明被测系统或压测机已无法按设定节奏完成请求 |
| P95 / P99 | 大多数请求与最慢一小部分请求的延迟 | 持续上升表示请求开始排队或某个依赖变慢 |
| HTTP 错误率 | 4xx / 5xx 等失败请求比例 | 5xx 上升通常表示服务或依赖无法正常处理 |
| `dropped_iterations` | k6 未能按固定到达率及时发起的请求数 | 仅适用于 `constant-arrival-rate`、`ramping-arrival-rate` 等到达率型 executor；持续增加表示已接近或进入饱和，它不是 HTTP 请求失败 |
| 最大 VU 数 | 为维持目标到达率实际需要的虚拟用户数 | 快速上升说明接口变慢；还要结合压测机 CPU 判断是否为压测机先到上限 |

### 2. API：Go 服务进程

| 看什么 | 从哪里看 | 可能说明的问题 |
| --- | --- | --- |
| CPU、内存、网络 I/O | `docker stats` | CPU 长期接近多核上限，可能是业务组装、JSON 编解码、缓存调用或 Go 调度压力；内存持续上涨要警惕堆积 |
| CPU profile | pprof `/debug/pprof/profile` | 定位具体耗 CPU 的 Go 函数，例如 Feed 组装、序列化、JWT 校验或数据库驱动 |
| heap profile | pprof `/debug/pprof/heap` | 内存持续上涨、GC 频繁或 CPU 热点不明确时，检查是否有大量对象分配或内存长期保留 |
| goroutine profile | pprof `/debug/pprof/goroutine` | 大量 goroutine 堆在同一调用栈，通常表示在等 MySQL、Redis、网络 I/O 或锁 |
| block / mutex profile | pprof 对应端点，按需开启采样 | 用于确认 Go 内部阻塞或锁竞争；必须先在代码中设置 `runtime.SetBlockProfileRate`、`runtime.SetMutexProfileFraction` 才会有有效样本，没有有效样本时不能据此下结论 |

### 3. MySQL：数据库服务

| 看什么 | 从哪里看 | 可能说明的问题 |
| --- | --- | --- |
| MySQL 容器 CPU、内存、网络 I/O | `docker stats` | CPU 高说明 SQL 执行、排序、扫描或并发处理压力大 |
| 磁盘 IOPS、读写延迟、磁盘队列 | 宿主机监控，例如 Linux `iostat -x`、Windows 性能监视器或云盘指标 | 排序落盘、刷盘或高并发写入时，磁盘可能先于 CPU 成为瓶颈；`docker stats` 不提供这组指标 |
| `Threads_running` | `SHOW GLOBAL STATUS` | 持续升高表示同时真正执行的 SQL 增多，数据库可能在忙于执行或排队 |
| `Threads_connected` | `SHOW GLOBAL STATUS` | 当前 MySQL 连接数；持续接近 MySQL 最大连接数时要警惕连接耗尽 |
| InnoDB 锁等待 / 活跃事务 | `SHOW ENGINE INNODB STATUS`、`information_schema.innodb_trx` | 事务互相等待行锁时，SQL 慢不一定是 CPU 或磁盘问题；读接口通常优先级较低，写入与活动类接口必须关注 |
| 慢查询、执行计划、语句耗时 | slow query log、`EXPLAIN`、performance_schema | 确认具体 SQL 是否扫描过多数据、缺索引或执行过慢 |

### 4. MySQL：API 的 Go 连接池

通过 API 调试端点读取：`GET http://127.0.0.1:6060/debug/db/stats`。

| 看什么 | 含义 | 如何判断 |
| --- | --- | --- |
| `max_open_connections` | API 允许同时打开的最大 MySQL 连接数 | 连接池硬上限，不是当前正在使用数 |
| `open_connections` / `in_use` / `idle` | 已打开、正在使用、空闲连接数 | `in_use` 经常接近上限时，连接池压力较大 |
| `wait_count` | 从 API 启动以来因无空闲连接而等待的次数 | 同一轮压测前后取差值；增量大说明请求确实在等连接 |
| `wait_duration_ms` | 上述等待的累计时间 | 与 `wait_count` 一起看，用于量化连接池排队对延迟的影响 |

注意：MySQL 的历史最大连接数不能单独证明 Go 连接池在等待；必须以 `wait_count` 和 `wait_duration_ms` 的压测前后增量为准。

### 5. Redis：缓存与时间线

| 看什么 | 从哪里看 | 可能说明的问题 |
| --- | --- | --- |
| Redis 容器 CPU、内存、网络 I/O | `docker stats` | CPU 高可能来自大量 ZSET、MGET、Lua 或网络编解码；内存接近限制有淘汰或 OOM 风险 |
| `SLOWLOG GET` | `redis-cli SLOWLOG GET` | 有慢命令时可定位具体 Redis 命令是否执行时间过长 |
| 命令类型与调用次数 | 实际调用链、必要时采样客户端指标 | 例如关注流会读多个 ZSET；高并发下应确认多次 Redis 往返是否成为主要成本 |
| 缓存命中情况 | 业务缓存指标或 MySQL 回源量 | 缓存未命中会把压力转移给 MySQL，不能只看 Redis CPU |

### 6. RabbitMQ 与 Worker：只在异步链路压测时看

`listLatest`、`getDetail`、`listByFollowing` 的请求内不直接发送 MQ 消息，因此压测这类读接口时 MQ 不是第一观测对象。测试发布、点赞、评论、活动报名等异步链路时，再关注：

| 看什么 | 可能说明的问题 |
| --- | --- |
| 队列消息数、Ready / Unacked | 消费速度跟不上生产速度，出现消息堆积 |
| Consumer 数量、Worker CPU / 内存 | Worker 并发不足、消费者阻塞或处理过慢 |
| 重试、死信队列数量 | 消费失败、重试耗尽或消息格式、依赖异常 |

### 7. 推荐读数顺序

```text
k6：QPS、P99、错误率、缺发
→ API：CPU、内存、goroutine、pprof
→ MySQL：服务 CPU / SQL 状态 + Go 连接池等待
→ Redis：CPU、内存、Slowlog、命令调用密度
→ 异步接口才看 RabbitMQ 队列与 Worker
→ 最后判断是单点瓶颈，还是整条链路一起接近上限
```

## 标准压测流程

适用于接口性能压测。目标是得到可复现的稳定吞吐、性能拐点、瓶颈证据和优化前后对比，而不是只跑出一个 QPS 数字。

```text
1. 明确目标、场景和通过标准
   → 固定被测接口、请求内容、数据规模、缓存状态和用户身份
   → 预先定义 P99 响应时间、错误率等通过标准
   → 定义停止条件，例如错误率超过 5% 或服务出现资源耗尽风险

2. 隔离压测环境
   → 确认使用独立压测环境，不混入生产或共享业务流量
   → 启动 API、MySQL、Redis、RabbitMQ 等所需依赖

3. 校准压测机
   → 确认压测机的 CPU、网络、文件描述符和 k6 能力足够
   → 避免将压测机先达到的性能上限误判成服务端瓶颈

4. 验证连通性和监控能力
   → 验证压测机可以访问 API，MySQL、Redis 等依赖正常
   → 确认日志、容器资源采集、MySQL 状态和 pprof 入口可用

5. 准备固定数据和鉴权材料
   → 准备固定的用户、视频、时间线、缓存、点赞关系和有效 Token
   → 测试期间不改变数据规模、缓存状态、服务实例数和请求内容

6. 准备并校验压测脚本
   → 固定请求路径、方法、请求体、鉴权材料、目标 QPS、时长和虚拟用户上限
   → 固定响应正确性校验、通过标准和结果输出位置
   → 先进行脚本语法检查和低负载试跑，确认脚本本身不会污染结果

7. 预热
   → 先以低负载运行，让连接池、缓存和运行时进入稳定状态
   → 预热阶段的数据不计入正式结果

8. 阶梯加压
   → 使用固定到达率模式控制目标 QPS
   → 每个档位分为预热期和正式采样期
   → 记录实际 QPS、P95/P99、错误率、缺发和压测机/API/MySQL/Redis 资源指标
   → 关键档位运行 2～3 次，排除偶发抖动

9. 定位与回归
   → 某档位不通过时，结合 MySQL 状态、pprof、容器资源和日志定位原因
   → 修复后必须在相同数据、相同请求、相同 QPS 下复测
   → 用优化前后的指标证明修复有效

10. 饱和态验证
   → 在通过标准边界之后继续提高压力，直到触发停止条件
   → 在饱和档延长压测时间，观察持续退化、资源耗尽或消息积压

11. 输出结论
   → 写清测试范围、固定条件、稳定 QPS、性能拐点和饱和表现
   → 给出瓶颈证据、优化前后对比，以及结论的适用边界
```

### 固定到达率模式

固定到达率模式指压测工具按设定节奏尝试发起请求，例如目标为 2,000 QPS 时，每秒尝试发起 2,000 个请求。接口变慢时，工具不会主动降低目标请求速率；如果无法按时发起请求，会记录 `dropped_iterations`。因此它适合观察系统在持续输入压力下的性能拐点。
