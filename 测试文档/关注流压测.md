# `POST /feed/listByFollowing` 压测记录

## 0. 测试环境准备与业务验证

在开始 QPS 压测前，先准备并验证推拉结合的真实业务链路：

- 普通作者发布后，视频会 fan-out 到粉丝收件箱；
- 大 V 发布后，视频只写作者发件箱；
- 关注流读侧会合并用户收件箱和所关注大 V 的发件箱；
- 作者跨越 `10,000` 粉丝阈值后，发布路径会从推模式切换为拉模式。

### 0.1 运行环境

| 组件 | 状态 | 用途 |
| --- | --- | --- |
| API | Docker 容器运行中，`127.0.0.1:8080` | 提供发布、关注与关注流接口 |
| Worker | Docker 容器运行中 | 消费时间线消息并更新 Redis 时间线 |
| MySQL | Docker 容器运行中 | 保存账户、关注关系与视频事实数据 |
| Redis | Docker 容器运行中 | 保存收件箱、作者发件箱、拉模式标记与关注列表缓存 |
| RabbitMQ | Docker 容器运行中 | 承接视频时间线事件 |

### 0.2 数据规模

| 数据组 | 账户/作者 | 关注关系 | 历史视频 | 作用 |
| --- | ---: | ---: | ---: | --- |
| 普通作者组 | 2,001 个账户，其中 1 名作者 | 2,000 | 100 | 验证普通作者 fan-out，形成 2,000 个收件箱写入目标 |
| 大 V 作者组 | 10,000 个账户，其中 10 名作者 | 100,000 | 1,000 | 验证大 V 不 fan-out、读侧拉取多个作者发件箱 |
| 阈值切换关系 | 1 名测试用户额外关注第 1 名大 V 作者 | 1 | — | 将该作者从 9,999 粉丝提升至 10,000 粉丝，验证切换 |
| 合计 | 12,001 个测试账户、11 名测试作者 | 102,000 | 1,100 | 供本轮压测使用 |

压测夹具实际包含 99 个可用登录用户令牌；这些用户均已配置为关注 1 名普通作者和 10 名大 V 作者。以 `limit=20` 读取时，服务最多从收件箱取 20 个候选，再从 10 个大 V 发件箱各取 20 个候选，即最多 220 个候选 ID 后再去重、查视频实体并排序。

测试夹具和令牌文件保存在 `loadtest/generated/`，其中可能含访问令牌，不提交仓库或复制到测试文档。

### 0.3 时间线任务分工

```text
API：发布视频事务写入 videos 和 outbox_msgs → 轮询 Outbox → 投递 RabbitMQ
Worker：消费时间线事件 → 更新 Redis 时间线
```

API 与 Worker 均已重建且为 healthy；`go test ./...` 通过。

### 0.4 已验证的业务结果

| 验证项 | 实际结果 | 结论 |
| --- | --- | --- |
| 普通作者发布 | 视频 `11131` 写入作者发件箱；2,000 名实际粉丝的收件箱均能查到该视频 | fan-out 生效 |
| 大 V 发件箱 | 10 名大 V 均存在 `feed:pull_authors` 标记，且初始测试视频均在各自作者发件箱 | 拉模式作者数据已就绪 |
| 阈值前发布 | 作者 `3003` 在 9,999 粉丝时发布视频 `11132`；普通粉丝收件箱中存在该视频 | 阈值前走推模式 |
| 阈值切换 | 测试用户关注作者 `3003` 后，其粉丝数变为 10,000，拉模式标记存在 | 切换条件生效 |
| 阈值后发布 | 作者 `3003` 在 10,000 粉丝时发布视频 `11133`；粉丝收件箱中不存在，但作者发件箱存在 | 阈值后停止 fan-out，走拉模式 |
| 关注列表缓存 | 测试用户缓存有 11 个关注作者，且 ready 标记存在 | 读侧可使用完整关注作者列表 |
| 真实接口合并 | `limit=20` 的关注流返回视频 ID 无重复且排序正确 | 收件箱与作者发件箱正确合并 |

本轮只验证了阈值 `9,999 → 10,000` 的升级切换，未验证降级回推模式；未覆盖冷数据、依赖故障和分页边界。

## 1. 测试目标与范围

测试已登录用户读取第一页关注流时，推拉结合热路径的稳定吞吐与性能拐点。

固定请求：

```json
POST /feed/listByFollowing
{
  "limit": 20,
  "latest_time": 0
}
```

本轮只测 Redis 热路径：关注列表缓存、用户收件箱、作者发件箱、拉模式作者标记和视频实体缓存均已准备；不测冷数据回源、翻页边界、Redis/MySQL 故障和未登录请求。

## 2. 固定环境与数据

| 项目 | 条件 |
| --- | --- |
| 压测工具 | Linux `loadtest` 虚拟机，8 个逻辑 CPU，k6 v2.2.0 |
| 被测 API | Windows Docker Compose 中的 API，压测机访问 `http://192.168.86.1:8080` |
| 依赖 | API、Worker、MySQL、Redis、RabbitMQ 均为 healthy |
| 测试用户 | 99 个登录用户轮换，请求头携带短期 JWT |
| 关注关系 | 每名压测用户关注 1 名普通作者和 10 名拉模式作者 |
| 普通作者数据 | 2,000 名真实粉丝；已验证真实发布可 fan-out 到全部收件箱 |
| 大 V 数据 | 10 名作者、每名 10,090 粉丝、合计 1,012 条已预热作者发件箱视频 |
| 返回校验 | 每次必须 HTTP 200，并返回 20 条 ID 唯一的视频 |

读侧每个请求会读取用户收件箱，并对 10 名大 V 分别读取作者发件箱；最多形成 220 个候选视频 ID，再去重、获取视频实体、按时间排序，并批量查询当前用户对返回视频的点赞状态。

## 3. 脚本与执行方式

脚本：[loadtest/following_feed_hot.js](F:/GoProjects/Agora/loadtest/following_feed_hot.js)。

使用 k6 `constant-arrival-rate` 固定到达率模式：接口变慢时不自动降目标，而是记录 `dropped_iterations`，因此可以识别持续输入压力下的性能拐点。用户令牌按请求序号轮换，避免单一用户导致测试偏差。

本轮的结果判定采用：HTTP 错误率低于 1%、响应校验通过、无明显缺发，并以 P99 低于 50ms 作为“稳定热路径”的延迟目标。脚本在执行前未将 P99 阈值写成 k6 自动阈值，以下结论以原始汇总中的实际 P99 为准。

## 5. 饱和态诊断

在 3,000 QPS 持续档期间采样到：

| 指标 | 采样值 | 含义 |
| --- | ---: | --- |
| API 容器 CPU | 约 0.08% | API 不是 CPU 计算饱和 |
| MySQL 容器 CPU | 约 4.38% | MySQL 不是 CPU 饱和 |
| Redis 容器 CPU | 约 0.41% | Redis 不是 CPU 饱和 |
| MySQL `Threads_connected` | 41 | 当前活动连接较多 |
| MySQL `Max_used_connections` | 80 | 已触及 API 配置的 `max_open_conns=80` 上限 |

`buildFeedVideos(...)` 在构造每一页响应时会调用 `LikeRepository.BatchGetLiked(...)`，即使视频实体命中缓存，也会对当前用户和本页视频执行一次 MySQL 批量点赞状态查询。同时，推拉合并路径还包含关注列表读取、拉模式作者批量筛选、11 个 ZSET 范围读取、视频缓存获取、排序和 JSON 序列化。

首次采样中 `Max_used_connections=80` 只说明 MySQL 历史上曾出现 80 个连接，**不能单独证明 Go API 的连接池在等待**。为确认这一点，后续补充 API 调试端点：

```text
GET http://127.0.0.1:6060/debug/db/stats
```

返回 `max_open_connections`、`open_connections`、`in_use`、`idle`、`wait_count` 与 `wait_duration_ms`。其中后两项从 API 进程启动起累计；每轮压测前后各取一次快照并计算差值，就能直接证明该轮是否有请求在等待 MySQL 连接。

### 5.1 连接池等待复测

API 重启后的基线为 `wait_count=0`、`wait_duration_ms=0`。在不重启 API 的前提下连续完成以下档位，因此每一行的等待值表示该档位相对上一快照的增量：

| 目标 QPS | 时长 | 实际 QPS | P99 | HTTP 错误 | 缺发 | `WaitCount` 增量 | `WaitDuration` 增量 | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1,000 | 60s | 999.96 | 7.10ms | 0% | 0 | 0 | 0ms | 稳定 |
| **1,500** | **60s** | **1,499.87** | **9.94ms** | **0%** | **0** | **0** | **0ms** | **当前稳定通过档** |
| 2,000 | 60s | 1,998.15 | 120.14ms | 0% | 90 | 0 | 0ms | P99 超出目标，出现少量缺发 |
| **2,500** | **60s** | **2,499.76** | **40.85ms** | **0%** | **0** | **260** | **1,164ms** | **当前稳定通过档** |
| 3,000 | 60s | 2,989.36 | 228.78ms | 0% | 381 | 0 | 0ms | 尾延迟拐点，未达到连接池等待 |
| 3,500 | 60s | 3,022.20 | 1,417.03ms | 0% | 24,622 | 4,302 | 23,986ms | 明显饱和 |

复测结论分为两个阶段：

- 2,000 QPS 虽然 P99 升至 120ms，但等待指标为零，因此当时不能归因于 MySQL 连接池；
- 2,500 QPS 下开始出现少量连接池等待，但 P99 仍为 40.85ms，接口稳定通过；
- 3,000 QPS 时 P99 已升至 228.78ms、出现缺发，但仍未出现新增连接池等待，说明此时并非单一连接池问题；
- 3,500 QPS 时实际吞吐只能达到约 3,022 QPS，P99 达 1.42 秒、缺发 24,622 次，且新增 4,302 次连接池等待、累计约 24 秒，属于明确饱和。

因此，在当前单 API、热数据条件下，`listByFollowing` 的**稳定持续吞吐为 2,500 QPS**；性能拐点位于 2,500～3,000 QPS 之间，3,500 QPS 是本轮停止档。连接池等待会在饱和后出现，但不是 2,000～3,000 QPS 尾延迟抬升的唯一原因；不能只靠调大 `max_open_conns` 解决问题。

### 5.2 各组件在饱和档的表现

3,000 QPS 运行中途采样到 API CPU 约 641%、MySQL CPU 约 129%、Redis CPU 约 96%，说明三者都在接近当前环境的处理上限：

- API 需要完成 JWT 校验、关注作者读取、1 个收件箱和 10 个作者发件箱范围读取、视频组装、点赞状态查询与 JSON 序列化；
- MySQL 每个请求仍会通过 `BatchGetLiked(...)` 批量查询当前用户对本页视频的点赞状态；
- Redis 每个请求包含关注列表读取、拉模式作者批量判断、多个 ZSET 范围读取和视频缓存读取；
- 3,500 QPS 时 k6 最大虚拟用户达到 2,210，且出现 24,622 次缺发。压测机也可能接近压力，但被测端 API、MySQL、Redis 已有明显负载，不能把结果简单归因于压测机。

因此 3,500 QPS 的 P99 达 1.42 秒不是单点故障，而是 API 计算、MySQL 查询、Redis 多次读取、连接池等待和压测端维持固定到达率的共同结果。

## 6. 有效性与边界

- 所有纳入结果的档位都使用 99 个轮换登录用户，并校验返回 20 条唯一视频；
- 有一次 2,000 QPS 持续测试因 JWT 到期产生 401，已明确剔除，未纳入上表；随后刷新令牌后完成有效复测；
- 本轮没有修改业务实现，也没有针对连接池进行优化；因此不存在“优化前后提升”的结论；
- 结果只适用于当前 Windows Docker 单 API 容器、当前 MySQL/Redis、当前测试数据及网络环境；多 API 实例、不同缓存命中率或更多拉模式作者需要重新测试。
