# 点赞异步链路压测

## 当前测试对象

```text
POST /like/like
→ MySQL：like_states + like_intent Outbox
→ Outbox Poller：Publisher Confirm 后发布 like.intent
→ Like Worker：事务更新 like_states、videos.likes_count、videos.popularity
→ MySQL：like_applied Outbox（仅真实点赞时）
→ Outbox Poller：Publisher Confirm 后发布 like.applied
→ Popularity Worker：Redis Lua 事件去重 + 当前分钟热度桶累加
```

本轮测的是完整异步写入链路，而不仅是 API 响应时间。API 成功代表点赞 Intent 已可靠写入 MySQL Outbox；之后还必须确认 Intent 与 Applied 队列排空、点赞状态与视频计数正确、Redis 热度桶已更新。

## 固定测试条件

- 请求：`POST /like/like`，JSON Body 为 `{"video_id": <测试视频 ID>}`；

### 结果分析

1. API 与消费者是两条不同的能力边界。API 只完成校验、限流、点赞状态版本递增和 Intent Outbox 写入；它不等待 Worker 落库完成。
2. Like Worker 是当前链路的吞吐短板。QPS 越高，请求结束时 `like.intent.events` 的积压越大；请求停止后仍需要时间排空。
3. Popularity Worker 在采样时没有形成可见积压，说明当前 Redis Lua“事件去重 + 分钟桶累加”的消费能力高于 Like Worker。
4. MQ 的作用在这里是削峰和异步化，而不是提高 MySQL 的最终写入能力：高峰期先把请求接住，Worker 再按自身吞吐写库；若持续生产速率长期高于 Like Worker 的消费速率，队列会持续增长，最终仍需要扩展消费者、优化单条写入或设置背压策略。

## 吞吐优化与通知运行方式

### 1. Like Worker 消费吞吐

当前 `like.intent.events` 只有一个 Like Worker，逐条处理消息。1500 QPS 仍能由 API 接住，但 Like Intent 队列会明显积压，说明单消费者的事务落库能力低于入口生产速率。

后续可按 `(userID, videoID)` 分片，让同一点赞关系的 like/unlike 保持顺序，再由多个独立消费者处理不同分片。消费者扩展后还需要事件版本号或操作时间，避免重试、延迟消息造成旧操作覆盖新状态；批量插入点赞关系、按视频聚合更新计数可作为下一阶段优化。

### 2. 通知持久化与 SSE 推送

`notification.like`、`notification.comment`、`notification.social` 和 `notification.activity` 由独立 Worker 消费。通知 Worker 查询必要的发送者或视频信息并写入 `notifications` 表，再通过 Redis Pub/Sub 广播在线通知；各 API 实例订阅该频道，只向本机持有的 SSE 连接推送。

```text
LikeApplied / CommentApplied / Social / ActivitySuccess
→ Notification Worker：写 MySQL 通知记录
→ Redis Pub/Sub：发布实时通知
→ 各 API 实例订阅并推送本机持有的 SSE 连接
```

Redis Pub/Sub 只负责在线实时提醒；离线或断线用户通过通知列表接口从 MySQL 拉取历史通知，因此不会把 Pub/Sub 当作持久化事实来源。

当前端到端完成吞吐的首个瓶颈位于 Outbox Poller，而不是 RabbitMQ 队列：Poller 单协程逐条执行“发布 → 等待 Publisher Confirm → 删除 Outbox 记录”。点赞 Intent 和 LikeApplied 事件共用该投递通道，因此在 500 QPS 输入下会先在 `outbox_msgs` 积压，随后逐步补发。

在优化 Poller 的并行 Confirm、批量删除或分事件类型投递能力之前，不应直接把同一端到端场景继续提升到更高 QPS；否则只会扩大已确认的 Outbox 积压，无法区分后续组件的实际能力。

## Outbox 批量 Confirm 优化与复测

### 优化过程

上一轮 500 QPS 基线中，API 能稳定受理点赞，但 Outbox Poller 对每条消息都执行一次“发布 → 等待 Confirm → 删除”的串行流程；Like Intent 与 Like Applied 因此先积压在 MySQL Outbox。

调整后：

```text
每轮查询最多 100 条 Outbox
→ 按事件类型分组
→ 同类型消息连续发布
→ 按 DeliveryTag 收取各自的 Confirm
→ 已 ACK 的记录批量删除
→ Nack / 超时的记录保留并延后重试
```

不同事件类型使用各自的 Publisher 与 AMQP Channel，在同一轮中并发投递；主轮询协程会等待本轮各组结束后才查询下一批，避免重复取到尚未完成的 `pending` 记录。

### 当前结论

批量 Confirm 后，500 QPS 下 API 受理稳定，Outbox 不再出现此前的数万条积压；发布端瓶颈已被移除。

压测停止后，`like.intent.events` 曾出现积压，原因是 Like Worker 仍按单条消息执行 MySQL 事务更新。当前端到端吞吐边界已转移到 Like Worker 消费速度。

## Like Worker 并行消费对比（500 QPS）

Like Worker 的单条 MySQL 事务是上一轮的主要积压点，因此将同一 Worker 进程内的 Like Worker 数量设置为常量 `LikeWorkerCount = 4`。四个消费者各自持有独立 AMQP Channel，其他 Worker 数量不变。

### 请求结果

| 项目 | 单 Like Worker 基线 | 4 个 Like Worker |
| --- | ---: | ---: |
| 压测模型 | 500 QPS，60 秒 | 500 QPS，60 秒 |
| 实际请求数 / 实际 QPS | 30,001 / 499.94 | 30,001 / 499.94 |
| HTTP 错误率 | 0% | 0% |
| API P95 / P99 | 12.15 ms / 16.38 ms | 17.15 ms / 33.96 ms |
| 请求结束后 Like Intent 观察值 | 约 20,454 Ready / 50 Unacked | 约 1,723 Ready / 200 Unacked |

API 延迟略有上升，但仍在毫秒级；主要变化是 Like Intent 的积压显著下降。四个消费者各预取 50 条消息，因此同时处理中的 Unacked 上限约为 200。
