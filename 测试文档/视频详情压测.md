# `POST /video/getDetail` 压测记录

## 1. 测试目标

本轮测试视频详情接口的两条真实路径：

1. 详情缓存已命中的正常热路径；
2. 同一热点视频详情缓存失效后，大量并发请求是否会同时回源 MySQL。

代码实际使用的是 Redis 分布式锁，不是 singleflight。因此本轮重点验证的是：**缓存失效时，Redis 锁是否抑制 MySQL 缓存击穿。**

## 2. 固定环境与数据

| 项目 | 条件 |
| --- | --- |
| 被测接口 | `POST /video/getDetail` |
| 请求体 | `{"id":10020}` |
| 鉴权 | 不需要；该路由在当前代码中允许游客访问 |
| 固定热点视频 | MySQL 中已有视频 `id=10020` |
| Redis 详情缓存 Key | `v1:video:detail:id=10020` |
| 被测服务 | Windows Docker Compose：API、Worker、MySQL、Redis、RabbitMQ 均为 healthy |
| 压测机 | Linux `loadgen`，8 个逻辑 CPU，k6 v2.2.0 |
| 压测机到 API | `http://192.168.86.1:8080`，`GET /healthz` 返回 200 |
| 通过标准 | HTTP 错误率小于 1%；正常热路径 P99 小于 20ms |

测试前先用一次正常详情请求确认视频存在、接口返回 200，并预热详情缓存。

## 3. 实际调用链

```text
POST /video/getDetail
→ VideoHandler.GetDetail
→ VideoService.GetDetail
→ Redis GET v1:video:detail:id=10020

缓存命中
→ JSON 反序列化
→ 返回 Video

缓存未命中
→ Redis SET NX 获取 lock:v1:video:detail:id=10020
→ 获锁请求再次检查缓存
→ MySQL videos 按主键查询
→ Redis 回填详情缓存（TTL 5 分钟）
→ Lua 校验 token 后释放锁

未获锁请求
→ 每 20ms 再查一次缓存，最多等待 5 次
→ 读到回填后的缓存后返回
→ 等待仍失败时才走 MySQL 兜底
```

## 4. 使用的脚本

| 文件 | 用途 |
| --- | --- |
| `loadtest/get_detail_hot.js` | `constant-arrival-rate` 固定到达率，测试详情缓存命中时的稳定 QPS 和延迟。 |
| `loadtest/get_detail_cache_miss_burst.js` | `per-vu-iterations`，每个虚拟用户只请求一次；用于在缓存删除后集中请求同一视频。 |

两份脚本都校验 HTTP 200 和响应中的 `id=10020`。

## 5. 执行过程与结果

### 5.1 缓存命中：2,000 QPS 基线

条件：详情缓存已预热，固定请求同一视频，目标 2,000 QPS，持续 60 秒。

| 指标 | 结果 |
| --- | ---: |
| 实际请求数 | 119,962 |
| 实际 QPS | 1,999.26 |
| HTTP 失败率 | 0% |
| 响应校验 | 100% 通过 |
| P95 | 1.98ms |
| P99 | 2.60ms |
| `dropped_iterations` | 40（约 0.03%） |
| 最大 VU | 123 |

结论：在当前固定缓存命中条件下，2,000 QPS 能稳定跟随目标，P99 明显低于 20ms，正常热路径通过。

### 5.2 缓存命中：4,000 QPS 观察档

条件保持不变，仅提高目标到 4,000 QPS，持续 60 秒。

| 指标 | 结果 |
| --- | ---: |
| 实际请求数 | 235,768 |
| 实际 QPS | 3,929.32 |
| HTTP 失败率 | 0% |
| 响应校验 | 100% 通过 |
| P95 | 2.23ms |
| P99 | 3.38ms |
| `dropped_iterations` | 4,233（约 1.76%） |

这一档的接口延迟仍很低、无 HTTP 失败，但压测端出现较多未能按节奏启动的请求，实际 QPS 未完全达到目标。由于没有对该档进行压测机、API、MySQL、Redis 的完整资源诊断和重复验证，**不能将 4,000 QPS 直接认定为服务端性能拐点**；它只作为下一轮继续诊断的观察结果。

### 5.3 缓存失效：500 并发同视频突发

每一轮执行以下固定操作：

```text
删除 Redis 详情缓存 Key
→ 开启 MySQL general log
→ Linux k6 同时发起 500 个对 id=10020 的详情请求
→ 关闭 general log
→ 统计 videos 详情 SQL 的 Execute 次数
```

使用 MySQL general log 统计实际执行的 SQL：

```sql
SELECT * FROM `videos`
WHERE `videos`.`id` = 10020
ORDER BY `videos`.`id`
LIMIT 1
```

| 轮次 | 并发请求数 | HTTP 失败率 | 响应校验 | P95 | P99 | MySQL 视频详情 SQL 执行次数 |
| --- | ---: | ---: | --- | ---: | ---: | ---: |
| 第 1 轮 | 500 | 0% | 100% | 47.23ms | 75.19ms | 1 |
| 第 2 轮 | 500 | 0% | 100% | 37.31ms | 38.73ms | 1 |
| 第 3 轮 | 500 | 0% | 100% | 29.99ms | 33.07ms | 1 |

结论：三轮结果一致。每轮缓存删除后虽然有 500 个同视频并发请求，但 MySQL 详情 SQL 都只执行 1 次；其余请求等待缓存回填后从 Redis 返回。Redis 锁在当前环境下成功抑制了同一热点 Key 的并发回源。

## 6. 结论与边界

可以确认：

- 缓存命中的 `getDetail` 热路径在 2,000 QPS、60 秒下稳定，P99 为 2.60ms；
- 同一视频缓存失效后，500 个并发请求不会将同一详情查询放大为 500 次 MySQL 查询；
- 三次突发中 MySQL 详情 SQL 都只有 1 次，分布式锁的核心效果得到直接证据支持。

本轮不能确认：

- 4,000 QPS 的 `dropped_iterations` 是 Linux 压测机、网络还是服务端资源所致；需要对该档重复运行并同步采集四方资源指标后才可归因；
- 分布式锁相对“完全不加锁”的延迟和数据库收益差值。当前代码没有运行时关闭锁的开关，如需严格 A/B 对比，应在单独测试分支临时绕过锁后再测；
- 多 API 实例下的锁效果。本轮只有当前单 API 容器，但 Redis 锁本身是跨实例共享的。
