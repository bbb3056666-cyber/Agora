账号与鉴权

9 项
流程 1注册（公开）
  1. Body：username（3～32 位字母数字）+ password（8～72 位）
  2. Redis 按 IP 限流：每小时最多 5 次
  3. Service：bcrypt 生成密码哈希
  4. MySQL：插入 accounts；username 唯一索引裁决重复注册
  5. 成功：200 account created；重复用户名：409
流程 2登录（公开）
  1. Body：username + password
  2. Redis 按 IP 限流：每分钟最多 10 次
  3. MySQL：按 username 查询 Account
  4. Service：bcrypt.CompareHashAndPassword 校验密码
  5. Redis：读取 token_version（未命中视为 0）；签发短期 JWT Access Token
  6. 生成随机 Refresh Token；仅将 SHA-256 哈希、状态 active、7 天过期时间写入 refresh_tokens
  7. 成功：200 返回 token、refresh_token、account_id、username
流程 3Refresh Token Rotation 完整流程
  1. Body：refresh_token
  2. MySQL：对明文 Token 做 SHA-256，以 token_hash 查询 refresh_tokens
  3. 校验存在、未过期、状态 active；再读取所属 Account
  4. 同一事务：条件撤销旧 Token（status=active 且 hash 匹配，原因 rotated）→ 生成并插入新 Refresh Token 哈希 → 签发新 Access Token
  5. 旧 Token 条件更新成功：200 返回新 Token 对
  6. 旧 Token 已 rotated 或并发刷新导致条件更新 0 行：判定复用 / 异常刷新
  7. 安全处置：撤销该用户全部 active Refresh Token，并 INCR Redis token_version，使旧 Access Token 失效
  8. 无效、过期或已撤销：401 invalid refresh token
流程 4退出登录（JWT 鉴权）
  1. Header：Authorization Bearer Access Token；JWT 中间件校验签名、过期、token_version、黑名单
  2. Body：refresh_token
  3. MySQL：将该 Refresh Token 状态改为 revoked，原因 logout
  4. Redis：将当前 Access Token 的 jti 写入 blacklist，TTL 为剩余有效期
  5. 成功：200
流程 5修改密码（公开）
  1. Body：username + old_password + new_password
  2. MySQL 查询账号；bcrypt 校验旧密码；bcrypt 生成新哈希
  3. MySQL：更新 accounts.password
  4. 随后撤销全部 active Refresh Token（password_changed）并 INCR Redis token_version
  5. 成功：200；校验失败：400
流程 6修改用户名（JWT 鉴权）
  1. Body：new_username；身份取自 JWT 上下文 accountID
  2. 读取 token_version，按新用户名签发新的 Access Token
  3. MySQL 更新 accounts.username；唯一索引处理重名
  4. 成功：200 返回新的 token；重名：409
流程 7资料修改接口（JWT 鉴权）
  1. 上传头像：multipart 文件 → 校验图片类型与大小 → 写本地 uploads → MySQL 更新 avatar_url → 返回 URL
  2. 更新个人资料：Body avatar_url / bio → 去除空白、过滤空更新 → MySQL 更新指定字段
流程 8账号查询接口（公开）
  1. 按 ID 查询：Body id → MySQL 查询 Account → 返回基础资料
  2. 按用户名查询：Body username → MySQL 查询 → 返回 id、username
  3. 查看个人主页：Body account_id → 查询账号、内容数、获赞总数、粉丝数、关注数 → 组合返回 Profile
流程 9受保护接口共用 JWTAuth：解析 Bearer Token → 校验签名与过期 → Redis 检查 token_version 和 jti 黑名单 → 写入 accountID / username / jti 到请求上下文
该节点是本模块的设计结论。

内容发布与分发

10 项
流程 1查看作者内容（公开）
  1. 输入作者 ID，MySQL 按 author_id 查询 contents
  2. 批量预加载 content_assets，避免逐条查询多图资源
  3. 统一返回视频、多图和文章；没有内容时返回空数组
流程 2查看内容详情（公开）
  1. 输入 content_id，先查进程内 L1 缓存，再查 Redis 内容缓存
  2. 缓存未命中时回源 MySQL：读取 contents，并预加载 content_assets
  3. 按 content_type 返回对应字段：视频地址、按序图片列表或文章正文
  4. 回填 Redis 与本地缓存；不存在时返回 404
流程 3上传视频资源（JWT 鉴权）
  1. multipart 上传视频文件，用户身份来自 JWT 上下文
  2. 校验文件存在、大小和扩展名，生成随机文件名并写入本地上传目录
  3. 返回 play_url；资源上传与正式发布分离，此时尚未创建内容记录
流程 4上传图片资源（JWT 鉴权）
  1. multipart 上传图片，校验大小及 jpg、jpeg、png、webp 等允许格式
  2. 生成资源 URL；多图内容发布时可提交 1～9 张图片
  3. 图片顺序不依赖请求或数据库默认顺序，而由 content_assets.sort_order 明确保存
流程 5发布视频内容（JWT 鉴权）
  1. Body 指定 content_type=video，并提交标题、描述、play_url、cover_url 与标签
  2. Service 按视频规则校验：播放地址和封面不能为空，清理其他类型专属字段
  3. MySQL 同一事务写 contents、标签关系和 content_published Outbox
  4. 事务提交后即可返回；后续时间线分发由 Worker 异步完成
流程 6发布多图内容（JWT 鉴权）
  1. Body 指定 content_type=image，提交标题、描述、1～9 个图片 URL 与标签
  2. MySQL 同一事务写一条 contents 主记录，以及多条 content_assets 图片记录
  3. 每张图片保存 sort_order；第一张图片可作为默认 cover_url
  4. 同一事务写标签关系与 content_published Outbox，任一步失败整体回滚
流程 7发布文章内容（JWT 鉴权）
  1. Body 指定 content_type=article，提交标题、正文 body、可选封面与标签
  2. Service 校验正文非空；文章正文保存在 contents.body，封面仍是统一摘要字段
  3. MySQL 同一事务写内容、标签关系与 content_published Outbox
  4. 时间线只保存 content_id 和发布时间，不复制大段正文
流程 8发布后的异步分发
  1. Outbox Poller 批量读取 pending 消息，发布 content_published 并等待 RabbitMQ Publisher Confirm
  2. Timeline Worker 消费事件，把 content_id 写入 Redis 全局时间线和作者发件箱
  3. Redis / MySQL 取得作者粉丝数：普通作者批量 fan-out 到粉丝收件箱；大 V 标记为读侧拉取
  4. 消息重复投递时，ZSET member 仍是同一 content_id，因此写时间线天然幂等
流程 9删除内容（JWT 鉴权）
  1. 按 content_id 查询内容并校验当前用户是作者
  2. MySQL 删除内容；关联资源和标签关系按模型约束清理
  3. 删除 Redis 与本地内容缓存，后续读取不再返回该内容
流程 10大文件分块上传与断点续传（JWT 鉴权）
  1. 初始化：Redis 按用户与文件哈希创建 24 小时上传会话，返回 upload_id 和已完成分块
  2. 上传分块：校验所属用户、索引与哈希，将文件块写入临时目录；重复分块直接视为成功
  3. 查询进度：从 Redis 会话返回已上传编号；客户端只补传缺失块
  4. 完成：确认分块齐全后按索引合并，删除临时文件和 Redis 会话，返回资源 URL

限额活动报名

5 项
流程 1查看内容活动（公开）
  1. Body：content_id
  2. MySQL：按 content_id 查询活动列表；没有活动时返回空数组
流程 2创建活动（JWT 鉴权）
  1. Body：content_id、标题、描述、名额、开始时间、结束时间
  2. 校验参数、时间窗口和名额；名额上限 100000
  3. MySQL 查询内容；只有内容作者可以创建活动
  4. MySQL：插入 content_activities，初始 remaining_quota 等于 quota
  5. Redis：写活动 Hash（剩余名额、开始/结束时间），TTL 到活动结束后 24 小时
  6. 成功：201 返回活动；内容不存在 404，非作者 403
流程 3活动报名完整流程
  1. Body：activity_id；报名用户身份取自 JWT
  2. Redis Lua 原子校验：活动存在、时间窗口、一人一单、剩余名额
  3. 预扣成功：HINCRBY 剩余名额 -1，SADD 用户到报名 Set；同一脚本设置 Set TTL
  4. 预扣失败：未开始 / 已结束 / 已报名 / 名额不足，直接返回业务错误
  5. 预扣成功后：发送 activity.register 消息，写 Redis 报名状态 PENDING，API 返回 202
  6. MQ 明确发送失败：Redis Lua 补偿，移除用户并恢复名额
  7. ActivityWorker：消费消息，在 MySQL 事务中插入报名记录 + remaining_quota > 0 条件扣减库存
  8. MySQL：活动+用户联合唯一索引与 event_id 唯一约束，保证最终一人一单和重复消息幂等
  9. 落库成功：写 Redis SUCCESS，发布 activity.success；通知 Worker 写活动成功通知
  10. 落库失败：Worker 在本地按 1 秒、2 秒、4 秒重试；最终失败则补偿 Redis 名额并写 FAILED
流程 4查询报名结果（JWT 鉴权）
  1. Body：activity_id；查询当前登录用户
  2. 优先读取 Redis 结果：PENDING / SUCCESS / FAILED
  3. 结果缓存未命中：MySQL 查报名记录；无记录时再查 Redis 预报名 Set
  4. 返回 SUCCESS、PENDING、FAILED 或 NOT_REGISTERED
流程 5设计取舍：Redis 负责高并发预扣与快速拒绝；MySQL 是最终账本；MQ 将落库削峰，允许报名结果短暂最终一致
该节点是本模块的设计结论。

点赞

3 项
流程 1点赞 / 取消点赞完整流程
  1. 输入：content_id；用户身份取自 JWT；接口返回 202 PENDING
  2. API 事务：like_states 按 (用户、内容) 原子递增 version，并写入 like_intent Outbox
  3. Outbox Poller 批量发布 LikeIntent；收到 Broker Confirm 后标记消息已投递
  4. LikeIntentWorker：仅处理 version 大于 applied_version 的意图，抵抗消息延迟重试导致的乱序
  5. MySQL 事务：更新 likes_count、首次点赞热度和 like_states 的最终状态 / applied_version
  6. 真实生效后写 like_applied Outbox；热度与通知由下游独立消费
  7. Worker 失败：1 秒、10 秒、60 秒延迟重试；最终进入死信队列
流程 2查询是否点赞（JWT 鉴权）
  1. 输入：content_id；按 (用户、内容) 查询 like_states.is_liked
  2. 返回 is_liked；异步意图尚未被 Worker 应用时，结果仍可能是前一状态
流程 3查看我的点赞内容（JWT 鉴权）
  1. MySQL 从 like_states 筛选 is_liked=true，再关联查询内容列表
  2. 无记录时返回空数组，不返回 null

评论

3 项
流程 1评论发布完整流程
  1. 输入：content_id、content；先由 API 校验参数并查询评论者资料
  2. API 生成 CommentIntent，事务写 comment_intent Outbox 后返回成功
  3. CommentWorker：MySQL 事务插入评论、更新 contents.comments_count、写 comment_applied Outbox
  4. source_event_id 唯一约束：MQ 重投不会重复插入同一条评论
  5. comment_applied 再驱动热度计算与通知；消费者失败走延迟重试和死信队列
流程 2删除评论（JWT 鉴权）
  1. 输入：comment_id；Worker 校验评论归属后删除
  2. 先写删除意图 Outbox，再异步删除评论并更新内容评论数；删除不增加热度
流程 3查看内容评论（公开）
  1. 输入：content_id
  2. MySQL 按内容查询评论；无评论时返回空数组

关注关系

5 项
流程 1关注完整流程
  1. 输入：vlogger_id；当前用户身份取自 JWT
  2. MySQL 同一事务：插入 socials 关系 + authors.follower_count 原子加一；唯一约束防止重复关注多计数
  3. 提交后刷新 Redis 关注作者 Set、粉丝数缓存和大 V 拉模式标记
  4. SocialWorker：从作者发件箱取近期内容，补入新粉丝收件箱
流程 2取关完整流程
  1. MySQL 同一事务：仅删除到一条关系时，才将 follower_count 减一，最低为零
  2. 提交后从 Redis 关注 Set 移除作者并校正拉模式标记
  3. SocialWorker：从收件箱移除该作者仍保留在发件箱中的近期内容
流程 3查看粉丝列表（JWT 鉴权）
  1. 可传 vlogger_id；不传则查看当前用户粉丝
  2. MySQL 查询粉丝资料，并单独读取真实 follower_count 返回
流程 4查看关注列表（JWT 鉴权）
  1. 可传 follower_id；不传则查看当前用户关注作者
  2. MySQL 查询作者资料，并返回关注数量
流程 5查看关注 / 粉丝数（JWT 鉴权）
  1. 粉丝数优先 Cache Aside 读取 Redis，未命中回源 MySQL；关注数由 MySQL 统计

Feed：最新流、热榜、关注流

6 项
流程 1最新内容完整流程
  1. 输入：limit、latest_time；带 JWT 时额外返回当前用户 IsLiked
  2. 热数据：Redis ZSET feed:global_timeline 按发布时间存最近 1000 个 content_id
  3. 按时间游标 ZREVRANGEBYSCORE 取 ID；第一页从最新开始，后页以 last_time 为上界
  4. 批量内容实体：L1 本地缓存 → L2 Redis MGET → L3 MySQL IN 查询；按输入 ID 顺序重组
  5. L1：进程内短 TTL 缓存，消除同一 API 实例上的重复反序列化与 Redis 请求
  6. L2：Redis 保存内容 JSON；MGET 批量读取，命中后回填 L1
  7. L3：MySQL 批量查缺失内容；回填 Redis 与 L1；singleflight 合并同 Key 并发回源
  8. 冷数据：请求游标落到 ZSET 最老时间之前，直接按 create_time 查询 MySQL，不污染热时间线
  9. 跨冷热边界：热 ZSET 不足一页时，再从 MySQL 补齐剩余数量
  10. 时间线丢失：singleflight 仅让一个请求从 MySQL 取最新 1000 条重建 ZSET，其余请求复用结果
  11. 构造响应：批量查询点赞状态，避免逐内容查询造成 N+1；返回内容列表、next_time、has_more
流程 2热门内容完整流程
  1. 输入：limit、as_of、offset；首次请求由服务端确定分钟级快照时间
  2. 互动真实生效后发送事件；PopularityWorker 用 Redis Lua 原子按 event_id 去重并写入对应分钟 ZSET
  3. 分钟桶：hot:content:1m:yyyyMMddHHmm；桶与事件去重标记保留 2 小时，覆盖计算与重试窗口
  4. 读榜：取最近 60 个分钟桶；按 30 分钟半衰期计算权重，越新的互动贡献越高
  5. Redis ZUNIONSTORE 合并为快照 ZSET；快照缓存 5 分钟，as_of + offset 保证翻页期间榜单稳定
  6. 按排名取 content_id，再复用三级内容缓存与批量点赞状态查询构造响应
  7. Redis 不可用：MySQL 按 popularity、create_time、id 的复合游标排序降级查询
流程 3关注内容完整流程
  1. 输入：limit、latest_time；当前用户身份取自 JWT
  2. 内容发布后：始终写全局时间线与作者发件箱 feed:author:{authorID}
  3. 按作者 follower_count 判断：少于 10000 为普通作者；达到阈值为拉模式作者
  4. 普通作者：Timeline Worker 游标分页读取粉丝；Redis Pipeline 批量 ZADD 到 feed:follower:{followerID}，每个收件箱保留 1000 条
  5. 大 V：不 fan-out；Redis Set feed:pull_authors 标记；发布侧按当前粉丝数兜底校正陈旧标记
  6. 读侧先从用户收件箱取 limit 个候选 ID
  7. 从 social:following 取关注作者，SMISMEMBER 批量筛出大 V；逐个作者发件箱各取 limit 个候选 ID
  8. 合并收件箱与大 V 发件箱候选：content_id 去重 → 批量读实体 → 按 create_time DESC、id DESC 排序 → 截取 limit
  9. 冷数据或 Redis 异常：MySQL 通过关注关系子查询按作者内容回退，天然覆盖普通作者和大 V
  10. 关注 / 取关后：SocialWorker 用作者发件箱补齐近期内容或移除近期内容；历史边界受 1000 条保留上限约束
流程 4按点赞数浏览（公开，可选 JWT）
  1. 输入：limit、likes_count_before、id_before；limit 限制为 1～50，默认 10
  2. 复合游标必须同时传点赞数和内容 ID；避免同点赞数的内容跨页重复或遗漏
  3. MySQL：按 likes_count DESC、id DESC 查询 contents；后页条件为点赞数更小，或点赞数相同且 ID 更小
  4. 复用批量点赞状态查询构造 FeedContentItem；返回下一页两段游标与 has_more
流程 5按话题浏览（公开，可选 JWT）
  1. 输入：tag_name、limit；tag_name 必填，limit 限制为 1～50，默认 10
  2. MySQL：contents JOIN content_tags JOIN tags，按 tags.name 过滤并按 contents.create_time DESC 返回
  3. 复用 FeedContentItem 构造与批量点赞状态查询；无结果时返回空 content_list
  4. 当前接口只按 limit 取最新结果，没有分页游标；适合话题入口的简化浏览
流程 6共用原则
  1. Redis ZSET 只保存 content_id + 时间 / 热度分数，避免重复存放完整内容实体
  2. MySQL 是冷数据与缓存回退的最终事实来源；Redis 故障不阻断基本浏览
  3. 取舍：将高频排序与时间线放入 Redis，将完整实体和最终关系留在 MySQL；用异步写与读侧合并平衡写放大和读取成本

实时通知：MQ + Redis Pub/Sub + SSE

7 项
流程 1通知事件源：只消费已经真实生效的事实事件
  1. LikeApplied：仅真实点赞（action=like、change=1）→ 通知内容作者；自己点赞自己不通知
  2. CommentApplied：仅真实发布评论（action=publish）→ 通知内容作者；自己评论自己不通知
  3. 评论 @：从 CommentApplied.content 解析 @用户名，为每位被提及用户创建单独通知
  4. SocialFollow：关注关系提交后产生事件 → 通知被关注作者
  5. ActivitySuccess：报名已由 ActivityWorker 成功写入 MySQL 后 → 通知报名用户
  6. 不直接消费 LikeIntent / CommentIntent：它们只是请求意图，可能失败、重复或被后续操作覆盖
流程 2RabbitMQ 路由与独立 Worker
  1. like_applied、comment_applied、social.follow、activity.success 各自绑定到对应 notification 队列
  2. Worker 进程为四类通知队列各启动一个 NotificationWorker；每个消费者独占 AMQP Channel
  3. API 进程不消费 RabbitMQ：互动主链路与通知写库解耦，通知慢不会占用 API 的数据库连接
  4. 处理 MySQL 临时错误时本地按 1 秒、2 秒、4 秒重试；重试耗尽记录日志后 Ack 丢弃
流程 3通知持久化：MySQL 是可靠历史记录
  1. notifications：recipient_id、sender_id、type、target_id、content、is_read、created_at
  2. source_event_id 唯一索引：RabbitMQ 至少一次投递时，同一事件只插入一条通知
  3. @ 通知：用事件 ID + 接收者计算独立来源 ID；同一评论的不同被提及者互不冲突
  4. 先写 MySQL 再实时广播：即使 Redis 广播失败，用户仍能通过通知列表补回
流程 4Redis Pub/Sub：跨 API 实例的在线广播
  1. NotificationWorker 写库成功后，将通知 JSON 发布到 notification.realtime 频道
  2. 每个 API 实例订阅同一频道；收到后只检查并推送自己内存中持有的 SSE 连接
  3. 解决多实例问题：Worker 不需要知道用户连接在哪台 API；所有实例都收到广播，只有正确实例实际发送
  4. Pub/Sub 是瞬时广播，不持久化；订阅断开或用户离线时可能错过，但 MySQL 列表负责补偿
流程 5SSE 长连接：服务器主动推给浏览器
  1. 建立通知流（JWT）：浏览器用 EventSource 发起 GET 长连接；Token 放 query 或 Authorization Header
  2. SSE 中间件解析 JWT，取得 accountID；连接属于该用户
  3. SSEHub：每个用户、每个浏览器标签页各维护一个带缓冲 Channel；同一用户多页面都会收到通知
  4. Pub/Sub 收到通知 → SSEHub.Push 写入目标用户 Channel → Handler 按 data: JSON\n\n 格式写入响应并 Flush
  5. 响应头：text/event-stream、no-cache、X-Accel-Buffering=no、keep-alive，避免代理缓存或缓冲推送
  6. 每 30 秒发送 SSE 注释心跳，防止代理 / 防火墙切断空闲连接
  7. 浏览器关闭或断网使请求 Context 取消；Hub 移除并关闭对应 Channel；EventSource 可自动重连
  8. 单连接 Channel 满时丢弃这次实时推送，避免慢客户端拖住 Worker；历史记录仍在 MySQL
流程 6通知查询与已读接口（均需 JWT）
  1. 查看通知列表：MySQL 按 recipient_id、created_at DESC 查询最近 50 条
  2. 标记已读：传 id 时仅更新本人该条；不传时将本人全部通知置为已读
  3. 查询未读数：MySQL 统计当前用户 is_read=false 的记录
流程 7核心取舍：MQ 解耦事件与通知写库；MySQL 保证可追溯；Redis Pub/Sub + SSE 只优化在线实时体验，不承担可靠投递
该节点是本模块的设计结论。
9

RabbitMQ：可靠异步事件链路

6 项
流程 1职责：把 API 请求链路和耗时的异步工作解耦
  1. 内容时间线写入、点赞 / 评论最终落库、热度计算、通知、关注收件箱补齐、活动报名落库都由 Worker 异步处理
  2. 突发写入先进入队列缓冲，API 不需要等待所有下游处理完成；Worker 可单独扩容
  3. 代价：部分结果最终一致；消费者必须能处理至少一次投递带来的重复消息
流程 2基础拓扑：交换机 → 路由键 → 队列 → Worker
  1. 主业务使用 durable Topic Exchange：按 routing key 将事件路由到模块队列，可一条事件绑定多个下游
  2. 主要事件：content_published、like_intent、like_applied、comment_intent、comment_applied、social.follow、activity.register / success
  3. Applied 事实事件可同时路由到热度队列和通知队列；各消费者独立 Ack、失败与扩容互不影响
  4. 每个持续消费者和 Publisher 独占 AMQP Channel；Channel 不是 goroutine-safe，避免并发发送导致协议帧交错
  5. Exchange、Queue 均 durable；发布消息 DeliveryMode=Persistent，Broker 重启后仍可恢复
流程 3Outbox 可靠投递完整流程
  1. 业务事务内同时写事实数据和 outbox_msgs；事务提交即保证事件不会因 API 崩溃而丢失
  2. Worker 内 Outbox Poller 每秒扫描 pending 消息，按事件类型分组并发批量发布
  3. 同类消息先连续 Publish，再按 DeliveryTag 集中等待 Broker Confirm；不在 HTTP 请求中同步等待
  4. 仅收到 Confirm ACK 后才标记 Outbox 已投递；Nack、超时或网络不确定时保留 pending，下轮重发
  5. 不确定投递会造成重复消息：下游通过状态版本、source_event_id 唯一索引或 Redis Lua event_id 去重保证幂等
流程 4消息延迟重试完整流程
  1. Timeline、LikeIntent、CommentIntent Worker 处理失败时，不直接 Ack 原消息
  2. 将原消息带 x-retry-count 发布到该模块 retry Exchange；等待 Confirm 成功后才 Ack 原消息，避免重试过程丢消息
  3. 每个模块独立 1 秒、10 秒、60 秒三个延迟队列；按重试次数选择对应 routing key
  4. 延迟队列通过 x-message-ttl 到期；消息到期后成为死信，由 Broker 自动转发回原目标 Exchange 与 routing key，再次消费
  5. 超过 3 次不再投递延迟队列，原消息 Nack(false,false) 成为最终死信
流程 5死信队列：保留无法处理的最终失败消息
  1. 触发：Worker 拒绝且不回队、消息过期、或队列达到限制（当前主要使用重试耗尽后拒绝）
  2. 业务队列配置死信交换机 dlx.events，并以原队列名作为死信 routing key
  3. 每个业务队列对应自己的 .dlq；便于定位是哪条业务链路长期失败，而不是把所有失败混在一起
  4. 死信不表示自动修复；它保留排查证据，后续可人工分析、修复后再决定是否重放
流程 6可靠性边界：Outbox 保证最终尝试投递；Confirm 判断 Broker 是否接收；重试 / 死信处理消费失败；幂等处理不可避免的重复投递
该节点是本模块的设计结论。

整体架构与取舍

7 题
Q1请用 1 分钟介绍 Agora，解决了什么问题？
答

Agora 是一个支持视频、多图和文章的内容分发与互动系统。API 负责鉴权、发布和查询，Worker 负责可靠事件投递、异步互动、内容分发与通知；MySQL 保存业务事实，Redis 承担缓存、时间线、热榜和原子预扣，RabbitMQ 解耦高频写入及后续任务。目前根据发布时间、互动热度和关注关系进行规则分发。

Q2为什么拆成 API 进程和 Worker 进程？两者各自负责什么？
答

API 负责鉴权、参数校验和快速受理请求；Worker 负责 MQ 消费、Outbox 投递、时间线更新、互动落库和通知。这样耗时任务不会长期占用 HTTP 请求，也能分别扩容和隔离故障。

Q3MySQL、Redis、RabbitMQ 在项目中的数据边界分别是什么？
答

MySQL 是最终事实来源，保存账号、内容、关系和通知等长期数据；Redis 保存缓存、时间线、热榜和活动预扣等高频临时状态；RabbitMQ 只负责传递和缓冲事件，不作为最终数据仓库。

Q4哪些场景要求强一致，哪些可以接受最终一致？
答

必须一起成功的数据放在同一 MySQL 事务里，例如内容与 Outbox、关注关系与粉丝数、报名记录与库存扣减。Feed 时间线、热榜、点赞评论的异步生效和在线通知允许短暂延迟，通过重试、幂等和数据库回退保证最终正确。

Q5为什么没有将所有高频数据都放到 Redis？
答

Redis 速度快，但内存成本高，而且缓存可能过期、被淘汰或暂时不可用。因此只把高频访问和短期状态放 Redis，长期业务事实仍存 MySQL；缓存丢失时可以回源恢复。

Q6项目目前最大的技术亮点和仍存在的边界分别是什么？
答

亮点是 Outbox 可靠事件链路、Feed 冷热分离与推拉结合、互动版本控制、Lua 原子预扣。当前边界是内容文件仍在本地、部分分页仍用时间游标、Redis Pub/Sub 只保证在线实时体验；继续扩展时可接对象存储并完善监控和分片。

Q7如果从单机部署扩展到多 API / 多 Worker 实例，哪些设计天然可扩展，哪些需要调整？
答

API 使用共享 MySQL、Redis 和 JWT，Worker 使用 RabbitMQ 竞争消费，因此都可以水平扩容。需要调整的是本地内容文件应迁到对象存储，并统一评估数据库连接池、Redis 和 MQ 容量；L1 缓存允许实例间短暂不一致。

账号与鉴权

7 题
Q1为什么同时使用 Access Token 和 Refresh Token，而不是只用一个 JWT？
答

Access Token 有效期短，用于每次请求鉴权；Refresh Token 有效期长，只用于换取新令牌。这样既避免频繁登录，也能在凭证泄露时缩短 Access Token 的风险窗口。

Q2Refresh Token Rotation 的完整流程是什么？
答

客户端提交 Refresh Token；服务端对其做 SHA-256 后查库并校验状态和过期时间；随后在同一事务中撤销旧 Token、创建新 Token，最后返回新的 Access Token 和 Refresh Token。旧 Token 一经使用就不能再次正常刷新。

Q3Refresh Token 为什么只保存 SHA-256 哈希？数据库泄露后还安全吗？
答

数据库只保存哈希，泄露后攻击者不能直接拿它调用刷新接口。SHA-256 适合这里，是因为 Refresh Token 本身是高随机、不可猜测的值，不像用户密码需要慢哈希抵抗字典攻击。

Q4旧 Refresh Token 被再次使用时，系统如何判断和处置？
答

如果旧 Token 已因轮换被标记为 rotated 后又出现，系统将其视为可能泄露：撤销该用户仍有效的 Refresh Token，并提高 Redis 中的 Token Version，让旧 Access Token 一并失效。

Q5并发请求同时刷新 Token 会发生什么？客户端与服务端各如何处理？
答

两个刷新请求可能同时使用同一个旧 Token，但条件更新只允许一个成功；另一个会被视为复用并触发安全处置。因此客户端需要用 singleflight 思路让刷新操作单飞，避免多个请求同时刷新。

Q6Token Version 与 Redis 黑名单分别解决什么失效场景？
答

Token Version 用于一次性让某个用户此前签发的所有 Access Token 失效；黑名单按 jti 精确禁用某一个 Access Token。前者适合改密等全局失效，后者适合单次登出。

Q7修改用户名、改密码、登出后，旧 Access Token 和 Refresh Token 如何失效？
答

改密码会撤销有效 Refresh Token并提高 Token Version；登出会撤销当前 Refresh Token，并把当前 Access Token 的 jti 加入黑名单。修改用户名会返回带新用户名的新 Access Token；当前实现没有让旧 Access Token 立即全部失效，它会在原有效期结束后失效。

3

统一内容模型、发布与 Outbox

12 题
Q1为什么视频、多图和文章共用一张 contents 主表？
答

三类内容共享作者、标题、封面、发布时间、点赞数、热度和分发规则。统一主表后，互动表、时间线、缓存和排序都只认 content_id，不需要为每种类型复制一套链路。

Q2系统怎样区分三种内容，并保证字段组合合法？
答

contents.content_type 保存 video、image 或 article。Service 按类型校验：视频必须有播放地址和封面，多图必须有 1～9 张图片，文章必须有正文；不属于该类型的字段会被清理。

Q3多张图片为什么单独放 content_assets，如何保证展示顺序？
答

图片是一对多资源，塞进一个字符串不利于约束、排序和扩展。content_assets 保存 content_id、asset_type、url、sort_order，并对内容、类型和顺序建立唯一约束；查询时明确按 sort_order 排序。

Q4文章正文为什么放 contents.body，而不是 Redis 时间线？
答

正文属于内容实体，MySQL 才是事实来源；时间线只负责排序和定位，只保存 content_id 与时间分数。读取列表时再通过缓存或数据库批量取得实体，避免把大文本复制进多个时间线。

Q5一次内容发布事务里写哪些数据，为什么要放在一起？
答

事务写 contents、需要的 content_assets、标签及关联关系、content_published Outbox。它们共同表示一次完整发布；任一步失败都回滚，避免内容存在但资源、标签或后续分发事件缺失。

Q6数据库与消息队列双写不一致是什么，Outbox 如何解决？
答

数据库成功后进程可能在发 MQ 前崩溃；先发 MQ 又可能数据库回滚。Outbox 把业务数据和待发送事件写进同一 MySQL 事务，再由后台轮询器可靠投递，把跨系统双写转化为一次本地事务。

Q7为什么收到 Publisher Confirm 后才能标记 Outbox 已投递？
答

Publish 调用成功只代表客户端完成写入，不代表 Broker 已接收。Broker 返回 Confirm ACK 后才说明消息已由 RabbitMQ 接管，这时才能把对应 Outbox 标记为已投递。

Q8Confirm 丢失为什么会造成重复消息，如何处理？
答

消息可能已经到 Broker，但 ACK 在网络中丢失。轮询器无法确认，只能保留并重投 Outbox，所以链路是至少一次而不是恰好一次。消费者使用事件 ID、唯一索引或 ZSET member 幂等处理重复消息。

Q9标签与内容为什么是多对多关系？
答

一条内容可以有多个标签，一个标签也会聚合多条不同类型的内容，因此使用 tags 与 content_tags 关联表。标签名由唯一约束防重，发布事务中复用已有标签并写关联关系。

Q10分块上传和断点续传分别解决什么问题？
答

分块上传把大文件拆小，单块失败只需重传该块；断点续传通过 upload_id 查询已完成分块，只补缺失部分。Redis 保存短期会话和进度，磁盘保存分块文件，完成后按顺序合并。

Q11内容发布成功到出现在内容流，中间经过哪些组件？
答

API 提交内容、资源、标签和 Outbox 事务；Outbox Poller 发布 content_published；Timeline Worker 写 Redis 全局时间线与作者发件箱，再按作者粉丝量决定写扩散还是读扩散。

Q12以后增加音频等内容类型，需要改哪些地方？
答

主要增加类型常量、类型专属字段或资源约束、发布参数校验和展示 DTO。点赞、评论、标签、热榜、关注流、Outbox 和通知都围绕 content_id 工作，通常不需要复制整套链路。

4

Feed：最新流、热榜、关注流

12 题
Q1最新流为什么做冷热分离？Redis 热数据和 MySQL 冷数据如何划分？
答

Redis 只保留最近约 1000 条全局时间线作为热数据，较老内容由 MySQL 查询。大多数首页请求命中 Redis，降低数据库压力；深度翻页仍能从 MySQL 获得完整数据。

Q2Redis ZSET 中为什么只存 content_id 和分数，不直接存完整内容？
答

时间线只负责排序和定位，因此存 content_id 与时间或热度分数即可。完整内容统一走实体缓存，避免每条时间线重复保存大对象，也便于内容信息更新。

Q3三级缓存的读取顺序、回填逻辑与各层的职责是什么？
答

先查进程内 L1，再用 Redis MGET 批量查 L2，剩余未命中 ID 一次性从 MySQL 查询。下层命中后逐级回填，并按原 content_id 顺序重组，兼顾低延迟和数据库兜底。

Q4singleflight 解决什么问题？和分布式锁有什么区别？
答

singleflight 把同一进程内、同一个 Key 的并发回源合并成一次，其余请求等待并共享结果。它不跨进程，也不保存长期状态；分布式锁由共享存储协调多个实例，范围更大但成本也更高。

Q5全局时间线丢失时如何重建，为什么重建要避免并发回源？
答

发现全局时间线为空时，从 MySQL 读取最新 1000 条重建 ZSET。重建过程使用 singleflight，让同一 API 实例只有一个请求查库，其余请求复用结果，避免缓存失效瞬间同时压向数据库。

Q6什么是 N+1 查询？Feed 如何批量查询点赞状态避免它？
答

N+1 是先查出 N 条内容，再为每条内容单独查询一次附加信息，数据库请求随 N 增长。项目把内容 ID 汇总后批量查询点赞状态，再映射回每条内容。

Q7热榜为什么按分钟桶存储，又为什么采用 30 分钟半衰期？
答

每分钟一个 ZSET 可以保留互动发生时间，查询时合并最近 60 个桶。30 分钟半衰期表示互动每过 30 分钟贡献减半，让新内容有机会进入热榜，同时避免榜单变化过快。

Q8热榜 as_of + offset 快照分页如何避免翻页过程榜单跳动？
答

第一页由服务端确定 as_of，并生成对应热榜快照；后续页面一直使用相同 as_of，只改变 offset。这样翻页期间即使新的互动到来，也不会改变本次浏览的排名基础。

Q9关注流为什么采用推拉结合？普通作者和大 V 的阈值逻辑是什么？
答

普通作者粉丝少，发布时推到粉丝收件箱，读起来快；大 V 粉丝多，逐个推送会造成巨大写放大，因此只写作者发件箱，读取时再合并。当前阈值是 10000 粉丝。

Q10大 V 发件箱与用户收件箱如何合并、去重和排序？
答

先从用户收件箱取普通作者候选，再批量筛出关注的大 V，从每个大 V 发件箱取候选；随后按 content_id 去重、批量取实体，按发布时间降序和 ID 降序排序，最后截取 limit 条。

Q11为什么每个来源只取 limit 个候选内容仍能得到最终前 limit 条？
答

一个来源中排在第 limit 名之后的内容，前面已经至少有 limit 条来自同一来源、且都比它更新，所以它不可能进入所有来源合并后的前 limit 名。因此每个来源取 limit 条已经足够。

Q12按点赞数浏览为什么需要 likes_count + id 复合游标？
答

很多内容可能拥有相同点赞数，只用 likes_count 无法确定翻页边界。加入 id 作为第二排序字段后，顺序稳定，下一页可查询点赞数更小，或点赞数相同但 ID 更小的内容。

5

点赞、评论与关注关系

10 题
Q1点赞为什么区分 LikeIntent 与 LikeApplied 两类事件？
答

LikeIntent 表示用户想点赞或取消，可能尚未执行；LikeApplied 表示 Worker 已经成功修改最终状态。只有 Applied 才驱动热度和通知，避免失败、重复或已被新操作覆盖的意图产生副作用。

Q2同一用户快速点赞、取消、再点赞时，版本号如何防止旧消息覆盖新状态？
答

API 每次操作递增 version。Worker 只应用 version 大于 applied_version 的消息；如果新版先执行，旧版后来重试，旧版号已经不够新，会被忽略，因此不会把最终状态改回去。

Q3like_states 中 version 和 applied_version 分别表示什么？
答

version 是 API 已接收的最新操作版本；applied_version 是 Worker 已执行到的版本。两者相等表示最新意图已落地，不相等表示仍有更新的操作等待处理。

Q4为什么点赞状态按 (用户、内容) 加锁，而不是直接争抢 contents.likes_count 那一行？
答

版本顺序只需要锁定某个用户对某个内容的 like_state，不同用户互不阻塞。不过真正修改同一内容的 likes_count 时仍会竞争 contents 行锁；MQ 把这种竞争移出 HTTP 链路并进行缓冲，但没有彻底消除热点行。

Q5取消点赞为什么不让热度衰减，后续再点赞又为什么不重复加热度？
答

热度表示内容曾获得有效互动，不要求取消点赞时立即反向扣除。like_state 记录是否已经贡献过热度：第一次真实点赞增加，取消后保留该标记，之后再次点赞不重复增加。

Q6评论为什么也改成 Intent / Applied 异步链路？删除评论如何保证只有作者能删除？
答

评论写入也可能带来数据库和 MQ 双写问题，因此先持久化 Intent，再由 Worker 事务执行评论与计数，成功后产生 Applied。删除时根据 comment_id 和当前用户校验归属，不能删除他人评论。

Q7消息至少一次投递时，评论如何避免重复插入？
答

CommentIntent 带来源事件 ID，comments 表对 source_event_id 建唯一约束。同一 MQ 消息重复消费时，重复插入被数据库唯一约束挡住，不会新增两条评论或重复增加计数。

Q8关注关系插入和 follower_count 更新为什么必须在同一事务？
答

socials 关系是关注事实，follower_count 是它的冗余计数。如果分开提交，可能只成功一边。放在同一事务后，要么关系与计数都成功，要么一起回滚。

Q9重复关注、重复取关并发到达时，计数如何不多加或多减？
答

重复关注由关注关系唯一索引阻止，插入失败时事务不会增加计数；取关先删除关系，只有 RowsAffected 等于 1 才减计数，并使用 GREATEST 防止低于零。

Q10关注 / 取关后，为什么还要异步补齐或清理用户收件箱？
答

关注后，用户希望立即看到作者近期内容，因此 Worker 从作者发件箱补入收件箱；取关后则移除仍保留的近期内容。这是 Feed 展示状态的异步维护，失败不会回滚已经提交的关注关系。

6

限额活动报名

7 题
Q1高并发活动报名最核心的并发问题是什么？
答

大量用户同时报名时，最核心的是不能超卖，也不能让同一用户重复占名额。若把检查名额、检查用户和扣减拆开执行，并发请求可能同时通过检查。

Q2Redis Lua 脚本在一个原子操作中完成了哪些校验和修改？
答

Lua 一次完成活动是否存在、是否在时间窗口内、用户是否已报名、名额是否充足的判断；成功后同时扣减剩余名额、把用户加入报名 Set，并设置必要的过期时间。

Q3为什么不用普通 Redis 命令或分布式锁，而要 Lua？
答

多条普通 Redis 命令之间可能被其他请求插入，必须额外处理并发；分布式锁能实现，但多一次加锁、释放和异常处理。Lua 在 Redis 内串行、原子执行这段短逻辑，更直接。

Q4Redis 预扣成功、MQ 投递明确失败时如何补偿？
答

API 已预扣但 MQ 明确发送失败时，执行补偿 Lua：从报名 Set 移除该用户并把名额加回。补偿本身也要保持原子，避免只恢复一半状态。

Q5Redis 都做了一人一单和扣库存，MySQL 为什么还要唯一索引和条件扣减？
答

Redis 是高并发入口，但可能丢数据、过期或发生补偿异常。MySQL 才是最终账本：活动与用户联合唯一索引防重复订单，remaining_quota 大于零的条件更新防止最终超卖。

Q6为什么报名接口返回 PENDING / 202，而不是同步返回最终成功？
答

Redis 预扣成功只代表请求已受理，MySQL 报名记录还由 Worker 异步创建，所以返回 202 PENDING。客户端再查询结果，可得到 SUCCESS、FAILED 或仍在处理。

Q7活动 Worker 最终失败时，Redis 名额、报名状态与 MySQL 如何处理？
答

Worker 先进行有限次数本地重试；仍失败时执行 Redis 补偿，恢复名额、移除预报名用户，并把结果状态写为 FAILED。MySQL 只有事务真正成功时才留下报名记录和库存扣减。

7

实时通知与 SSE

8 题
Q1哪些已生效事件会触发通知？为什么不直接消费 Intent 事件？
答

真实点赞产生 LikeApplied，真实发布评论产生 CommentApplied，关注产生 SocialFollow，报名落库成功产生 ActivitySuccess；评论内容中的 @ 也由 CommentApplied 派生。Intent 只表示请求，可能失败或被覆盖，不能直接通知。

Q2通知为什么先写 MySQL，再发 Redis Pub/Sub？
答

MySQL 保存可靠的历史通知，Redis Pub/Sub 只负责在线实时提醒。先写库后广播，即使 Redis 暂时不可用或用户离线，用户以后仍能通过通知列表看到消息。

Q3通知表 source_event_id 唯一索引如何保证幂等？
答

每个业务事实事件都有 source_event_id，通知表对它建立唯一索引。RabbitMQ 重复投递同一事件时，第二次插入触发唯一冲突，Worker 将其视为已经处理。

Q4Redis Pub/Sub 不可靠，用户离线或订阅断开时通知会不会丢？
答

实时推送可能错过，因为 Pub/Sub 不保存消息。但通知已经先写 MySQL，用户重连或打开通知列表时可以查询历史记录，因此丢的是即时提醒，不是业务通知。

Q5多 API 实例下，为什么所有实例都订阅同一个频道？
答

用户的 SSE 连接可能在任意 API 实例上。所有实例都订阅频道后，每台都会收到广播，但只有持有目标用户连接的实例真正推送，Worker 不必知道连接位于哪台机器。

Q6SSE 与 WebSocket 的区别，为什么这里选择 SSE？
答

该场景主要是服务器单向推送，SSE 基于普通 HTTP，浏览器原生支持 EventSource 和自动重连，实现比双向 WebSocket 简单。若以后需要实时聊天、客户端持续上行，再考虑 WebSocket。

Q7SSE 如何鉴权、保持连接、发送心跳、处理断线重连？
答

客户端以 GET 建立长连接，Token 放在 query 或 Authorization 中；服务端验证 JWT 后登记用户 Channel，按 SSE 格式写数据并 Flush，每 30 秒发心跳。连接断开时 Context 取消并清理 Channel，EventSource 可重连。

Q8慢客户端导致本地推送 Channel 堆积时，为什么选择丢实时推送？
答

如果慢客户端一直阻塞，继续等待会拖住推送协程并影响其他用户。因此缓冲区满时放弃本次实时提醒；通知已经在 MySQL 中，用户仍可从列表获取。

8

RabbitMQ 可靠性、重试与死信

8 题
Q1为什么选择 RabbitMQ？Topic Exchange、routing key、queue 分别做什么？
答

RabbitMQ 提供灵活路由、消费者确认、Publisher Confirm、死信和队列隔离，适合本项目的业务事件。Topic Exchange 根据 routing key 把消息送到绑定队列，队列缓冲消息，Worker 从队列消费。

Q2Publisher Confirm 能保证什么，不能保证什么？
答

Confirm 能说明 Broker 接收了某次发布，避免生产者误以为消息已送达；它不能说明消费者已处理成功，也不能自动解决重复投递或数据库一致性，这些仍靠 Ack、重试和幂等。

Q3为什么 Confirm 要在 Outbox Poller 后台等待，而不是 HTTP 请求内等待？
答

若 HTTP 每发一条消息都等待 Confirm，请求延迟会直接受 MQ 网络影响。先把事件可靠写进 Outbox 后即可返回，再由 Poller 后台批量发布并等待确认，既可靠又不阻塞用户请求。

Q4消费者 Ack、Nack、requeue 的区别是什么？
答

Ack 表示处理完成并删除消息；Nack 且 requeue=true 表示放回原队列；Nack 且 requeue=false 表示不回原队列，若配置了死信交换机则进入死信链路。

Q5延迟队列如何通过 TTL + 死信交换机实现，而不是依赖特殊队列？
答

失败消息按次数发到 1 秒、10 秒或 60 秒延迟队列。队列设置 x-message-ttl，消息到期后由 Broker 按 x-dead-letter-exchange 和 routing key 转回原业务交换机，再进入消费队列。

Q6重试发布为什么要等 Confirm 成功后才 Ack 原消息？
答

如果先 Ack 原消息，再发送重试消息，而重试发布失败，消息会永久丢失。因此先发布到重试交换机并等待 Confirm，确认 Broker 已接管后才 Ack 原消息。

Q7消息为什么最终进入 .dlq？死信后如何排查与处理？
答

超过最大重试次数后，Worker 拒绝且不回队，消息按业务队列配置进入对应 .dlq。死信队列用于保留证据和隔离故障，需要记录日志，修复原因后再决定是否人工重放。

Q8为什么 RabbitMQ 至少一次投递必须配合业务幂等？项目中有哪些幂等方式？
答

生产者确认丢失、消费者处理成功但 Ack 丢失都会造成重复投递。项目分别使用状态版本、数据库唯一索引、Outbox 事件 ID和 Redis Lua 的事件去重，使同一消息重复执行也不改变最终结果。

9

性能测试、排障与演进

8 题
Q1你如何为 listLatest 设计压测场景，为什么固定热路径和数据集？
答

固定为登录用户访问 listLatest 第一页，参数有效、Redis 和 MySQL 正常、热数据及点赞关系预先准备。这样先测真实稳定热路径的吞吐和延迟，不让冷数据、异常请求等变量混入结果。

Q2为什么使用到达率型压测而不是只设置固定 VU？
答

到达率型压测直接规定每秒发起多少请求，接口变慢时仍保持目标压力，并通过 dropped_iterations 暴露压测机无法继续发请求。固定 VU 模式下接口越慢，VU 发出的请求反而越少，容易掩盖过载。

Q3压测前需要固定哪些变量，哪些变量应逐步变化？
答

固定代码版本、机器配置、容器数量、数据集、请求内容、测试时长和缓存状态；每轮只改变目标 QPS。先预热再采样，关键档位重复运行，才能把结果变化归因到压力。

Q4出现 P99 上升时，如何区分压测机、API、MySQL、Redis 或队列的瓶颈？
答

先看 k6 实际吞吐、错误率、P95/P99 和 dropped_iterations；再看压测机资源、API CPU与 goroutine、数据库连接等待和慢查询、Redis 延迟与命中率、MQ 堆积。沿调用链找最先异常的环节。

Q5database/sql 的 WaitCount、WaitDuration 说明什么？如何发现连接池等待？
答

WaitCount 是请求数据库连接时发生等待的累计次数，WaitDuration 是累计等待时间。对比压测前后的增量，如果 OpenConnections 接近上限且两者快速增加，说明请求在连接池排队。

Q6pprof 的 CPU、heap、goroutine、block / mutex profile 分别排查什么？
答

CPU profile 看计算热点；heap 看主要内存占用和分配；goroutine 看大量协程卡在哪里；block 和 mutex 看通道、锁竞争。后两类需要提前开启采样，没有样本不能直接判断没有阻塞。

Q7为什么一个服务的容器 CPU 很低，接口仍可能出现排队式高延迟？
答

CPU 低只表示没有忙于计算。请求仍可能在等待数据库连接、行锁、网络 I/O、Redis 或 MQ 响应；大量等待会形成队列，使 P99 不断上升，但容器 CPU 看起来不高。

Q8如果继续优化项目，你会优先优化哪些链路，为什么？
答

优先完善全链路指标和稳定复测，再针对证据优化数据库查询与连接池、Worker 并发和热点行；部署层面将本地内容迁到对象存储。不会在没有瓶颈证据时盲目把全部数据搬到 Redis。
